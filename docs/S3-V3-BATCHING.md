# S3 批量/对象数优化评估（逐对象 RTT、打包、并发、删除）

> 问题：逐对象 RTT 能否批量减少网络握手？批量是否最快、有没有必要？
> 测试：真实七牛 Kodo；对象 1KB；500 个对象；网络与 SDK 配置与产品一致。
> **并发口径（261026 用户批准）**：现行默认 = **12**（`DEFAULT_TRANSFER_CONCURRENCY` 与 `deleteMany`）；本文 §2.1/§2.2 的「并发 8」是当时基线数据，保留作对照；§2.3 是 8 → 12 的实测。

## 1. 结论先说

1. **S3 没有批量 PUT**。TLS/连接握手已由 SDK keep-alive 复用，剩下的是**每个对象一次请求-响应 RTT**；批量上传只能改协议（把多个对象打进一个 pack 对象）。
2. **批量 DELETE 有 API，但七牛上反而慢**：500 键单次 DeleteObjects 约 7.2s；并发单对象 DELETE（8 并发）约 1.2s/300 键（~4.1ms/键），快 3 倍以上。本轮已把 v3 `deleteMany` 改为并发单对象删除。
3. **pack（多对象打包）是唯一真正的“批量上传/下载”**：500×1KB 单对象 PUT 3.65s，10 个 pack PUT 仅 123ms（等效 30x）；整包 GET 82ms（等效 22x）。但**选择性读取仍是一次 Range 请求一个 RTT**；改/删要重写 pack 或 repack，和不可变索引/零痕迹设计冲突，**当前不做**。
4. **并发是更便宜的加速杠杆**：PUT 200 对象，1/4/8/16/32 并发 = 17/70/134/270/452 对象/s。项目硬约束现为 **12 并发**（261026 用户批准；本文测量时旧红线是 8），**不再上调到 16+**（provider 限流、内存、移动端）。

## 2. 实测数据

### 2.1 单对象 vs pack（500 × 1KB）
| 操作 | 耗时 | 等效对象/s |
|---|---|---|
| 单对象 PUT（并发 8） | 3,649ms | 137 |
| 单对象 GET（并发 8） | 1,840ms | 272 |
| pack PUT（10 × 50KB） | **123ms** | 4,065 |
| pack GET 整包（10 对象） | **82ms** | 6,098 |
| pack Range GET ×500（并发 8） | 1,544ms | ~324（请求数仍 500） |

- Range 测试中 SDK 对分段响应报了 content-md5 校验错误（500/500），该行只用于说明**请求数没有减少**，不代表数据读取成功。
- pack 的收益来自“一次请求搬 50KB”；只取其中 1 个小对象时仍要 1 次 Range 请求，**不会减少 RTT**。

### 2.2 删除策略（300~500 键，1KB）
| 策略 | 耗时 | 每键 |
|---|---|---|
| 单次 DeleteObjects 500 键 | 7,222ms | 14.4ms |
| 100 键 ×5 串行 | 7,288ms | 14.6ms |
| 100 键 ×5 并行 4 | 2,861ms | 5.7ms |
| 单对象 DELETE 并发 8（300 键） | 1,223ms | 4.1ms |
| 单对象 DELETE 并发 16（300 键） | 642ms | 2.1ms |
| 100 键 chunk 并行 8（300 键） | 1,502ms | 5.0ms |

**已落地**：`S3v3S3Remote.deleteMany` 改成并发单对象 DELETE（去重、失败抛出留给 pending 重试）；并发当时 8、现 12。真实 S3 集成（含彻底删除零痕迹/深度清理）通过。

### 2.3 并发 8 → 12 实测（用户批准）
| 操作 | 并发 8 | 并发 12 | 提升 |
|---|---|---|---|
| 单对象 PUT 500 个 | 124 对象/s | **197 对象/s** | +59% |
| 单对象 GET 500 个 | 273 对象/s | **408 对象/s** | +49% |
| v3 首次同步 1,000 文档（真实 S3） | 7.4~8.6s | **6.0s** | ~25~30% |
| v3 增量改 10 篇（真实 S3） | 710~832ms | **621ms** | ~20% |
| 其中 uploads 阶段 | 165ms | 78ms | — |
| 其中 pending 删除 | 176ms | 45ms | — |

已落地：`DEFAULT_TRANSFER_CONCURRENCY = 12`（引擎可配置 `transferConcurrency`，硬夹 32）；`deleteMany` 并发 12。**261026 用户批准以此定稿**。

## 3. 为什么“批量”不能简单用在 PUT/GET

- S3 API 是**对象级**的：PutObject/GetObject 没有多对象变体；`DeleteObjects` 是例外（多对象删除）。
- 连接复用后，单对象成本主要是**服务端处理 + 一次 RTT**；增加并发比“把请求攒起来”更直接（攒起来就是 pack）。
- `Multipart Upload` 只拆分**一个大对象**，不能合并多个小对象；它适合大附件，不适合 20 万个小附件。
- `S3 Batch Operations` 是给已有对象做批量作业（复制/标签/删除），不是客户端数据面。

## 4. 是否有必要上 pack（对象打包）

### 收益
- 首同步/全量重拉 20 万小附件：单对象 8 并发约 137/s（当时基线）→ 约 24min；现 12 并发约 1.5x；pack 可降到分钟级（按 30x 估算，实际受包大小/并发影响）。
- 删除 20 万对象：并发单删约 4.1ms/键 ≈ 14min；pack 后对象数少 2~3 个数量级，删除接近秒级。

### 代价
- 协议要升级：索引里增加“对象 → pack + offset + length”映射；上传以 pack 为单位（改一个对象可能重写整包）。
- 选择性下载要 Range GET，仍是每对象一个 RTT；只有“整包下载”才享受批量收益。
- 零痕迹删除要求 pack 可 compaction/repack；pack 内含活对象时不能直接删，GC 复杂度显著上升。
- 冲突/恢复/基线/测试全部要重做；出错面远大于当前单对象模型。

### 建议（按你的“到第二瓶颈再优化”原则）
| 数据量 | 建议 |
|---|---|
| ≤2 万文档 / 20 万附件 | **不做 pack**；首同步 12 并发（261026 定稿）约 15~20min 量级，增量 1.5~2.5s 已可接受 |
| 首同步成为主要抱怨，或附件 >20 万 | 先评估**临时提高首同步并发到 16**（实测约 2x，风险：provider 限流/移动端内存），不急着改协议 |
| ≥50 万附件，且全量重拉频繁 | 再做 pack v4（建议按内容寻址切 1~4MB pack，Range 读取，冷数据 pack、热数据单对象） |

## 5. 本轮已做的低风险优化
- `deleteMany`：并发单对象删除（七牛上 3 倍+，也避免单次 500 键 7s 的尖峰）；并发 12。
- 保留 `DeleteObjects` 不使用；若未来发现 provider 批量删除更快，可加 provider 自适应（当前无证据）。
- 不改上传/下载协议；并发上限已定稿 12（261026 用户批准），不再上调。
