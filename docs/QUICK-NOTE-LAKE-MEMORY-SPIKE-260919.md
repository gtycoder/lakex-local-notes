# 小记挂 Lake 底座 · 内存与延迟量化（260919 spike）

> **本文性质**：量化报告（spike），**不含功能实现**。
> 分支：`spike/quick-note-lake-memory`（worktree `../lake-notes-spike-memory`，基线 = master 线 `f39b968` 的干净检出）。
> 背景：用户要给小记支持更多格式（有序/无序列表、待办、引用、加粗、代码、图片、附件），在犹豫「直接挂 Lake 内核底座」是否太重。
> 关联：`docs/QUICK-NOTES-SPEC.md`（小记现状：纯 textarea + `.qnote`，独立数据空间）、`docs/LAKEX-CONTRACT.md`（内核契约）。

---

## 0. 结论先行

1. **「相当于多开一个 tab」这个判断成立**：多一个 Lake 编辑器实例的边际成本是 **+1.2 ~ +5 MB JS 堆**（小/中文档；44k 字的大文档约 +10 MB），进程 RSS 约 **+5.5 MB/实例**。
2. **24 个实例的实测总量（dev 构建）**：JS 堆 **142.7 MB**（1 个实例时 83.8 MB，即 23 个实例共 +58.9 MB）、DOM 节点 28,066、事件监听 43,750、Electron 进程树 RSS **≈925 MB**（1 个实例时 ≈799 MB）。
3. **成本是线性的**：第 14→24 个实例每一个都稳定 +1.2~1.4 MB 堆，没有出现非线性劣化 ⇒ 第 25 个实例（小记那条）与第 24 个同价。
4. **打开延迟可接受**：内核 `editor-perf init` **9~16 ms**（小/中文档），从点到可见 **≈140~180 ms**；44k 字大文档为 173 ms / 535 ms。
5. **附加发现（需要注意）**：反复开关标签后内存**不完全归还** —— 关掉 20+ 个标签只回收了约 18 MB（开时花了约 59 MB），0 标签稳态停在 ≈113 MB（fresh 启动是 ≈84 MB）。属于缓存/保留，不是本次结论的阻塞项，但值得单独记一笔。

**给小记决策的落点**：按「编辑时挂**一个**实例、关掉即销毁」做，增量就是上表里的一条 —— 约 1.5 MB 堆 / 5 MB RSS，相对 24 tab 的 925 MB 是 0.5%。**不要**做成「每条小记一个常驻实例」。

## 1. 测量方法（可复现）

**环境隔离**（全程不碰另一个会话的实例与数据）：

- 独立 worktree `../lake-notes-spike-memory`（分支 `spike/quick-note-lake-memory`），`node_modules` 软链主工作区（无第二份安装）。
- 独立 userData：把 `lake-notes-dev/workspace-default` 用 **APFS 克隆**（`cp -Rc`）到临时目录，SQLite 用 `.backup` 做一致性快照（避免读到运行中 WAL 的残页）。
- 独立端口：vite **1431**（主工作区 1421）/ CDP **9232**（主 9222）/ asset **19877**（主 19876）；`LAKE_DEV_SERVER_URL` 指向 1431。
- 克隆数据里的资源 URL 从 `:19876` 改写成 `:19877`（含 `.lake` 卡片值里的 URL-encoded 形式 `%3A19876%2F`），否则图片全 CORS 失败、会低估内存。
- `localStorage["lake-notes-v1.settings"].maxOpenTabs = 24`（**默认是 8**，不改的话开到第 9 个就开始 LRU 淘汰，测不出 24 实例）。

**测量口径**：

- 每个采样点：`HeapProfiler.collectGarbage` **连跑两次** → `Performance.getMetrics` 取 `JSHeapUsedSize` / `Nodes` / `JSEventListeners`（避免把未回收的浮动垃圾算进去）。
- 打开动作：在页面内对侧栏 `.tree-row` 派发 `click()`（窗口在后台时 CDP 的 `Input.dispatchMouseEvent` 收不到，这点与 HANDOFF 的记录一致）。
- 延迟：抓内核自己打的 `[editor-perf] init <id> <ms> ms` 控制台日志；另记「点击 → 新标签出现」的墙钟。
- 进程 RSS：对本 spike 实例的 Electron 进程树（父进程按 `--remote-debugging-port=9232` 定位）求和。

**原始数据**：`/tmp/lk-spike-measure4.json`（1→24 实例全量）、脚本见本工作区 `scripts/spike-lake-memory/`。

## 3. 结果：延迟

| 场景 | 内核 `init` | 点击→新标签可见 |
|---|---|---|
| 小/中文档（多数） | 9 ~ 16 ms | ≈140 ~ 180 ms |
| 中等（几段 + 图） | 40 ~ 80 ms | ≈330 ~ 410 ms |
| 大文档 `长大纲`（44k 字） | 173 ms | 535 ms |

⇒ 小记那种短内容是**最快的一档**；「点开小记编辑」的人工感知延迟约 0.15 s，不会破坏「短平快」的手感。

---

## 4. 附加发现：关闭标签后内存不完全归还

| 动作 | 结果 |
|---|---|
| 24 → 23 标签（关一个） | 堆 **-0.00 MB**（几乎不回收） |
| 连续关 20 个标签 | 堆 **-18.36 MB**（而开这 20 个花了 ≈+17 MB 的“纯边际”，但总量曾涨 +59 MB） |
| 全部关闭后稳态（0 标签，等待 1.2 s + 双次 GC） | 堆 **113.3 MB**；fresh 启动 0/1 标签是 **≈84 MB** |

解释与边界：

- 关闭瞬间不回收，主要是 React 卸载与内核 `destroy` 是异步的（等 1 s 后再测才看到下降）。
- 0 标签稳态比 fresh 高 ≈30 MB，指向**缓存/保留**（内容缓存、内核模块级缓存、已加载的懒加载 chunk）。
- 这**不是**本次小记决策的阻塞项，但说明「反复开关文档」不是零成本；若日后要做「小记编辑完就销毁实例」，建议顺手确认这条保留量不会随开关次数线性增长（本次只测了一轮）。

---

## 5. 结论与建议

1. 用户方案可行：**小记编辑时挂 1 个 Lake 实例**，成本 ≈ **1.5 MB 堆 / 5 MB RSS**，相对 24 tab 的 925 MB 占比 0.5%，感知延迟 ≈150 ms。
2. **仍建议「编辑态单实例」而不是「每条小记常驻」**：常驻 N 条 = N × 上述成本，且小记时间线通常一屏十几条，收益与成本不匹配。
3. 格式诉求（列表/待办/引用/加粗/代码/图片/附件）全部是内核原生能力，挂底座后「小记 → 文档」转换可从「手工序列化」退化为「搬字节 + 换根 id + 重写图片 src」，顺带消掉现存的「内核容忍形态」隐患（见 `QUICK-NOTES-SPEC` 与 HANDOFF §4 的字段口径差异记录）。
4. 若最终只想支持列表/待办/加粗这几样，轻量标记层仍然更省；但**当附件与图片也要进小记**时，挂底座的相对收益明显上升（媒体卡片的正确形态只有内核能产出）。

## 6. 复现步骤（给后续会话）

```bash
# 1) worktree + 依赖
git worktree add ../lake-notes-spike-memory -b spike/quick-note-lake-memory
cd ../lake-notes-spike-memory && ln -s ../lake-notes-electron/node_modules node_modules

# 2) 隔离数据（克隆 + 一致性备份；并改写资源端口到 19877）
SPIKE_HOME=$(mktemp -d "$TMPDIR/lake-spike-memory.XXXXXX")
mkdir -p "$SPIKE_HOME/workspace-default"
SRC="$HOME/Library/Application Support/lake-notes-dev/workspace-default"
cp -Rc "$SRC/notes" "$SRC/note-assets" "$SRC/history" "$SPIKE_HOME/workspace-default/"
sqlite3 "$SRC/metadata.sqlite3" ".backup '$SPIKE_HOME/workspace-default/metadata.sqlite3'"
# 端口改写：127.0.0.1:19876 → :19877，含 %3A19876%2F 的编码形式

# 3) 启动（vite 1431 / CDP 9232 / asset 19877；vite.config.ts 的 server.port 需临时改 1431）
LAKE_USER_DATA="$SPIKE_HOME" LAKE_CDP_PORT=9232 LAKE_ASSET_PORT=19877 \
LAKE_DEV_SERVER_URL=http://127.0.0.1:1431 \
node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 1431

# 4) 设上限并测量
#   localStorage['lake-notes-v1.settings'] = {"maxOpenTabs":24} → reload
#   node scripts/spike-lake-memory/measure.mjs        # 1→24 实例逐点采样
```

## 7. 口径与局限（写清楚免得被误用）

- **dev 构建**：React 未压缩、含 HMR client ⇒ 绝对值偏大；生产构建的堆/RSS 会更低。**相对量与线性结论不受影响**。
- **干净 HEAD 检出**：测量跑在 `f39b968` 的干净 worktree 上，**不含**另一会话在途的表格/FortuneSheet 改动。
- 真实数据来自 dev 库快照（287 篇量级），文档体量与图片分布是真实的；但**样本是单次跑**，没有做多次重复取均值。
- RSS 含 GPU/utility 进程，波动 ±30 MB；用趋势而非单点读数看。
- 未测：移动端（不同 WebView/dock 形态）、生产构建、25 个实例同时**处于编辑激活态**（本次只有 1 个激活、其余 keep-alive 隐藏）。
