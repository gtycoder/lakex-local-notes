# S3 同步重设计（草案 · 261025）

> 状态：**设计草案，未实施**。目标：产品语义与结果不变的前提下，把 S3 从「全局清单 + 永久墓碑」改成「当前状态 + 设备基线 + 锁」，实现**永久删除零痕迹**。
> 规模目标：**2 万文档 / 20 万附件**（不再按 10 万/100 万设计）。
> 配套：[SYNC-APPROACHES-SURVEY.md](./SYNC-APPROACHES-SURVEY.md)（同类做法）· [S3-MANIFEST-SCALE-RESEARCH.md](./S3-MANIFEST-SCALE-RESEARCH.md)（现状测算）。
> 审计：第一份（7/10 有条件 → 8/10 批准）；第二份（三轮：三项条件补齐后 **批准进入实施 8/10**）。处置见 §17–§20（本批文档修改，未实施）。

## 0. 一页结论

- **云端只存「现在活着的」**：正文、附件、一份全局元数据索引（文档/目录/回收站/锁/图标/排序/kind）、每篇文档一份资产声明、一个小指针。**没有墓碑、没有提交历史、没有全量资产清单。**
- **删除 = 缺席**：云端索引里没有这篇，就是被删了；判断依据是**每台设备本地的「上次同步基线」**，不是云端墓碑。
- **永久删除 = 立刻清空**：彻底删除一篇文档时，索引条目、正文对象、该文档所有附件、资产声明**当轮全部物理删除**；**应用可见对象零痕迹**（边界与部署约束见 §5.5；崩溃中断由下次同步的待删队列补删）。
- **并发 = 只锁发布窗口**：写索引之后、写指针之前取锁（通常 1~2 秒），发布前再读一次指针确认没被别人改过；锁失败等 3~5 秒重试一次，仍失败则报错稍后重试，绝不并发覆盖（详见 §6.1）。
- **长期离线 = 当新设备**：设备始终保留本地基线，长期离线回来仍能正确推断删除；只有「基线丢失 / 云端 epoch 变化 / 云端被重置」时才走全量重拉（用户已确认可接受）。
- **规模账**：2 万文档的全局索引约 **7–8MB 明文 / 2.5–3MB gzip**；20 万附件的声明拆成每篇文档一份（约 1KB），不再进全局索引；零变更同步只读一个约 200B 的指针；变更轮传索引 + 增量。

## 1. 设计目标与不变量

### 1.1 必须保持的语义（逐条映射）

| 现有语义 | 新设计如何保证 |
|---|---|
| 本地是真相，S3 只是镜像 | 不变：本地 DB + 文件仍是唯一真相，云端只镜像 |
| 先拉后推 | 不变：读指针/索引 → 应用远端 → 再推本地（只在发布窗口取锁） |
| 删除压编辑 | 基线里有、云端索引没有 ⇒ 远端已删；本地无论改没改都不上传，改过的先强制留历史快照 |
| 恢复是唯一显式例外 | 不变：本地 restore_pending 标记 ⇒ 本轮 local-wins，重新把条目加回索引并上传 |
| 冲突先提交者胜 | 不变：远端已发布的版本胜；本地被覆盖的版本强制写本地历史快照 |
| 回收站（软删）跨端可见、可恢复、可自动过期 | 不变：回收站条目仍是索引里的正常条目（带 trashedAt / deletedFromParentId），正文与附件保留；本地过期后才走彻底删除 |
| 排序 / 图标表情 / 编辑锁 / 文档类型 | 不变：仍在全局索引里，按 updatedAt / lockedAt 做字段级 LWW |
| 资产存在性 = 云端声明差集，禁止逐对象探测 | 保留原则，声明位置从「全局清单」改成「每篇文档一份资产声明」；上传/下载仍按声明差集，不做 HEAD |
| 历史快照只在本机 | 不变：历史不上云；被覆盖版本靠本地历史恢复 |
| 并发上限 12 | 261026 用户批准（8 → 12；实测首同步约 1.5x），仍是传输池上限 |
| 小记独立空间 | 不变：独立前缀、独立索引、独立正文与附件；与文档同一把锁、同一个指针提交 |
| 设备本地视图（缩放/选区/工作表/多维表导航） | 不变：不落正文、不进云 |
| 打开 = 只读（不因序列化差异写盘） | 不变（与同步层无关） |

### 1.2 明确改变的结果（需要用户接受）

1. **云端不再保留任何「应用可见的删除痕迹」**（边界见 §5.5：versioning/object lock/复制/服务端日志等属部署约束或范围外）：墓碑取消后，被永久删除的文档在云端没有条目、没有正文/附件、没有删除时间。**注意：现代的彻底删除在云端本来就没有内容副本**（purge 先物理删掉 `.lake` 才上传占位墓碑），所以实际变化是「去掉墓碑元数据痕迹」+「不再保留遗留墓碑可能携带的旧内容」；曾同步过它的其他设备仍会保留一份本地 purged 副本（可本地恢复，和现在一样）。恢复只能靠本机回收站 / 本地历史（用户已确认）。**小记是例外**：旧 quick-notes 通道的墓碑曾携带删除前正文+图片上云并被 GC 永久保护（该通道已删）；v3 只保留 `quick-notes` 索引的 `purged` id 数组（不带内容），去掉永久残留（净收益）。
2. **长期离线设备 / 云端重置 = 全量重拉**：视为新设备；本地未同步的编辑不再自动合并（用户已确认可接受）。
3. **设备必须保有基线**：基线丢失（重装、清数据、换机导入旧备份）按新设备处理——**只拉不推**，本地旧数据由用户显式导入。
4. **旧版本客户端**在迁移后必须升级（会看到「协议版本不兼容」，不会误写）。

## 2. 对象布局（协议 v3）

```
meta/pointer.json                      # 唯一可变小对象（约 200B）
meta/index/{indexHash}.json            # 全局元数据索引（文档/目录/回收站/锁/图标/排序/kind），gzip
meta/assets/{noteId}/{declHash}.json   # 每篇文档的资产声明（不可变、内容寻址；filename/size/hash），gzip
objects/{noteId}-{contentHash}.lake    # 正文（内容寻址，沿用现有）
assets/{noteId}/{filename}             # 附件/图片（沿用现有）
quick-notes/meta/index/{indexHash}.json    # 小记全局索引（含标签目录与关系字段）
quick-notes/meta/assets/{quickNoteId}/{declHash}.json # 小记图片声明（不可变、内容寻址；保留 mimeType/width/height）
quick-notes/objects/{contentHash}.qnote     # 小记正文（沿用现有）
quick-notes/assets/{quickNoteId}/{filename} # 小记图片（沿用现有）
```

**与现状的差异**：`manifests/latest.json` 与 `manifests/{commitId}.json` 全部废弃；`manifest.assets` 不再存在；提交链取消（只保留当前索引一份）；墓碑与 `deleted` 条目取消。

### 2.1 meta/pointer.json

```json
{
  "v": 3,
  "epoch": "随机 UUID，初始化云端时生成；用于识别云端被重置",
  "lake": { "commit": "索引内容 hash" },
  "quickNotes": { "commit": "索引内容 hash" },
  "generation": 123,
  "createdAt": "ISO 时间",
  "deviceId": "最后发布者（排障用，不参与判定）"
}
```

- 指针是**唯一**的可变对象；一次同步最多写一次，且永远最后写（先写对象与索引，再写指针）。
- 指针不存在但 `objects/` 或 `meta/index/` 非空 = 云端异常，按「用户确认」处理，不自动清空。
- **`epoch` 是什么**：这个云端数据仓库的「身份证」（随机 UUID，首次初始化时生成，之后每次同步都不变）。它跟 S3 配置/密钥无关，代表的是「这一堆云端数据的身份」。
- **`epoch` 不一致** = 本地记的那套数据和云端现在这套不是同一个世界（被重置、换目标、迁移）：提示「全量重拉（云端为准）」或「重新上传本地（覆盖云端）」，区别见 §15。
- **`generation` 是什么**：单调递增的发布流水号（每次发布 +1）。用来识别「云端被从旧备份回滚了」：epoch 相同但 generation 小于本地基线 ⇒ 云端退回了旧版本，不能按「缺席 = 删除」处理。
- 判断顺序：pointer 缺失 → 看云端空不空；epoch 不一致 → 换世界；epoch 相同但 generation 倒退 → 回滚；**epoch 相同、generation 相同但任一 commit 不同 → 分叉/迟到覆盖**（审计二轮 N4），停止增量、进入修复流程（§15），绝不按普通增量做缺席删除；都正常 → 增量同步。

### 2.2 全局元数据索引（meta/index/{hash}.json）

只放**做同步决策必需的元数据**，不放资产明细：

| 字段 | 用途 |
|---|---|
| `notes[]`: `id, title, parentId, sortOrder, updatedAt, contentHash, kind, icon, isLocked, lockedAt, isConflict, trashedAt, deletedFromParentId, assetsHash` | 冲突/下载/目录树/锁/回收站/恢复落点/资产声明引用 |
| `folders[]`: `id, title, parentId, sortOrder, nodeType, icon, updatedAt, trashedAt, deletedFromParentId` | 目录树与目录级回收站 |
| `tags[]`（仅小记索引，v3 唯一真相源）: 标签目录（id/name/createdAt/updatedAt/order/deleted 不设；删除=目录缺席） | 标签 LWW |
| 条目内 `tagIds, tagsUpdatedAt`（仅小记索引，v3 唯一真相源） | 关系 LWW |

- **没有 `assets` 明细字段**：条目只带 `assetsHash`（缺省 = 无资产），指向 `meta/assets/{noteId}/{declHash}.json`；声明对象不可变、只写一次。
- **没有 `deleted/deletedAt`**：删除就是条目不再出现在下一份索引里。
- 回收站条目保留在 `notes[]`（带 `trashedAt`），因此回收站的跨端可见/恢复/自动过期语义不变。
- 索引按内容 hash 命名且不可变；新索引发布成功后，旧索引对象随第 11 步删除（失败入待删队列），不留历史。
- **小记索引**（`quick-notes/meta/index/{hash}.json`）：`items[]` 字段 = `id, createdAt, updatedAt, contentHash, isConflict, assetsHash, tagIds, tagsUpdatedAt`；`assetsHash` 缺省 = 无图片，指向 `quick-notes/meta/assets/{quickNoteId}/{declHash}.json`（不可变；与 Lake 声明同一套规则，审计第三轮条件 1）。

### 2.3 资产声明（meta/assets/{noteId}/{declHash}.json，不可变）

```json
{ "noteId": "...", "assets": [ { "filename": "...", "size": 123, "hash": "sha256" } ] }
```

- **内容寻址、只写一次、不可变**（审计二轮 N1）：对象名就是内容 hash；索引条目用 `assetsHash` 指向它。**禁止按 noteId 原地覆盖**——那会在 pointer 切换前污染当前可达状态（旧正文 + 新声明）。
- 无资产 = 条目不带 `assetsHash`，且不写声明对象（不是空数组）。
- 作用与现有 `manifest.notes[].assets` 相同：上传只 PUT 声明里没有的缺失资产；下载按声明差集；不做 HEAD。
- 回收站条目继续保留 `assetsHash` 与资产对象（可恢复）；彻底删除时把该 id 的所有声明版本一并删除。
- 新声明写入并发布后，旧声明版本进入待删队列；门禁按「当前索引该 id 的 assetsHash ≠ 旧 declHash」判定（见 §5.2）。
- **不再有全局「在用集」**：GC 不再扫描全库，而是按「这篇文档这次变化的前后差」定向删除（见第 5 节）。


### 2.4 本地基线（设备端，不上云）

每台设备保存**上次成功同步后的索引快照**（lake 与小记各一份，gzip JSON，2 万文档约 2.5–3MB 磁盘）：

- 内容：与云端索引同构（lake：notes/folders；小记：items/tags——v3 的标签仍在 小记索引里，唯一真相源）。
- 另存 `baselineEpoch` 与 `baselineCommit`。
- 它是「删除推断」「冲突判定」「本轮需要上传什么」的唯一依据；替代现在的 `sync_base` 每篇 hash 账本。
- 更新时机：指针写成功之后（先落盘临时文件再原子替换；失败则下轮重试，不推进基线）。

## 3. 同步流程（一次完整同步）

```
0. **引擎入口硬闸（download-only 模式）**：baseline 缺失 → ①完整同步：上传清单恒空、**不发布索引、不写指针**；②小记单条推送：**拒绝**，提示先完成一次完整同步建立基线；③删除意图**休眠但保留**（不表达为上传、也不清除）；④restore_pending **不触发上传**（恢复例外的前提是参与同步；待用户显式导入后按正常恢复走）。本地数据需用户显式「导入」后才参与同步。
1. 读指针（**不取锁**）：GET meta/pointer.json（约 200B）
   - 不存在且云端为空 → 初始化 epoch（见 3.1）
   - 不存在但云端有对象 → 提示用户处理（不自动清空）
   - epoch 与本地基线不一致 → 提示「全量重拉 / 重新上传」二选一
   - epoch 相同、generation 相同但 commit 不同 → **分叉/迟到覆盖**：停止增量，走 §15 修复流程（先查本地删除意图）
2. 零变更快路径：pointer 的两个 commit（lake / 小记；标签在 v3.1 才独立）与本地基线相同 → 结束（只花了 1 次小 GET）
3. GET 变化的索引（gzip，一次；只读 commit 变了的那几个空间），校验版本与结构
4. 合并：按「基线 × 本地 × 远端」三方决策（见 4.2），生成下载清单与上传清单
5. 下载（正文、按需的资产声明、缺失资产），应用到本地
6. 上传（正文、资产、**不可变资产声明**）——**对象先写，索引后写**；声明用新 hash 新对象，绝不原地覆盖
7. 计算待删键并**立即写入本地待删队列**（先入队、后发布！不是失败才写）：被替换的旧正文、被移除的附件、被替换的**旧声明版本**、被彻底删除的文档前缀、旧索引对象
8. 写新索引对象（meta/index/{hash}.json 等，gzip；条目带 assetsHash）
9. **发布窗口取锁**（见 6.1）：
   a. 再读一次 pointer；若 commit 已变 → 释放锁，回到第 3 步重做
   b. 写 pointer（唯一一次，最后写，同时切换到新索引）
   c. 释放锁
10. 更新本地基线（提交号 + 快照）
11. 执行第 7 步的删除；成功的从队列移除，失败的保留下轮重试（见 5.2）
```

### 3.1 初始化 / 云端重置

- **新设备（无本地数据、无基线）**：只拉不推。按索引全量下载正文与附件，建立基线。
- **云端为空（pointer 缺失且无对象）**：初始化新 epoch；若本地有数据，**询问用户**「上传本地」还是「保持云端为空」。绝不静默上传（防误覆盖）。
- **pointer 缺失但云端有对象**：视为损坏/半迁移状态；只允许「全量拉取」或「用户确认后重建」，并先备份本地。
- **epoch 不一致**：云端被重置或换了存储；用户二选一：全量重拉（云端为准，本地多出的进备份区）或重新上传（覆盖云端），区别见 §15/§15.1。
- **epoch 相同但 generation 倒退**：云端被从旧备份恢复/回滚；同样走 §15 的二选一，绝不按「缺席 = 删除」处理。
- **换 S3 位置时会发生什么**：目标是**空桶/空前缀** → 没有 pointer，走「初始化」分支（询问上传本地或保持空）；目标是**有本应用旧数据的桶** → pointer 存在，按 epoch/generation 判断；同一个桶同一个前缀 → 什么都不变，不触发。

### 3.2 小记单条推送（「保存并同步」）在 v3 下的形态

现状 `quickNotePush` 是「读整份小记清单 → 只 upsert 这一条 → 无锁覆盖写」，v3 必须改成走发布锁的等价流程（审计 P3）：

1. 取**发布锁**（同 §6.1）；
2. 读 pointer，校验 epoch / generation 正常（异常 → **报错并给出与完整同步相同的「换世界」提示**，不静默退回完整同步）；
3. GET 当前小记索引 `quick-notes/meta/index/{hash}.json`，只修改这一条（其余条目与标签目录原样保留）；
4. 写**正文/图片/不可变声明**（对象先写）；把将被替换的旧正文、旧图片、旧声明版本写入待删队列（发布前入队）；再写新的小记索引对象（条目带 `assetsHash`）；
5. 再读 pointer 做 CAS 校验（必须仍等于第 2 步的 commit），通过后写 pointer：**小记 commit 换成新值，lake commit 原样保留**；
6. 放锁；更新本地小记基线（沿用 **I2 守卫** `markSyncedGuarded` 语义：推送期间用户又编辑 → 不推进基线，下轮重传）。

**推送前必须先看三方（base / local / remote），不能把「远端不存在」直接当远端删除**（审计第二份 P3-B）：

| base | local | remote | 单条推送结论 |
|---|---|---|---|
| 无 | 有 | 无 | **本地新建 → 上传**（这是新增小记的正常路径） |
| 有 | 有 | 无 | 远端彻底删除 → 删除压编辑；除非本机 restore_pending |
| 无 | 有 | 有 | 两端新建/同 id → 走完整冲突规则 |
| 有 | 有 | 有 | 常规更新，按 hash / updatedAt 决策 |

- 上传或替换正文/图片前，把将被替换/移除的对象（旧正文、旧附件、**旧声明版本**）写入待删队列（与 §5.2 同一门禁）。
- 「退回/拒绝」的判定（不静默降级）：①云端还没有 pointer/索引 → 走完整同步初始化；②**本机没有基线**（download-only 模式）→ **拒绝推送**，提示先完成一次完整同步建立基线（审计二轮 R2-2）；③三方命中「远端已删」→ 按删除压编辑处理并返回明确原因，不复活。

## 4. 合并与语义细节


### 4.1 基线的作用

基线 = 上次同步后的云端状态。每个决策都问三件事：`base` 有没有、`local` 有没有、`remote` 有没有。

**判定顺序固定**：① restore_pending（恢复例外，最高优先）；② 缺席/彻底删除判定；③ 常规改。下表**仅在 baseline 存在时适用**；baseline 缺失时引擎入口直接进 download-only（见 §3 第 0 步），不走上表。

### 4.2 决策表（文档级）

| base | local | remote | 结论 |
|---|---|---|---|
| 无 | 有 | 无 | 本地新建 → 上传（加入索引） |
| 无 | 无 | 有 | 远端新建 → 下载 |
| 无 | 有 | 有 | 两边都新建（同 id 只可能同一篇）→ 按 hash 冲突规则 |
| 有 | 无 | 有 | 本地已彻底删除（本地有删除意图标记）→ 删除胜：索引移除该条；本地删除意图**保留**（见下方说明） |
| 有 | 有 | 无 | 远端已彻底删除 → 删除胜：本地移入回收站并标 purged + 强制历史快照，不上传 |
| 有 | 无 | 无 | 两边都删 → 无事 |
| 有 | 有 | 有 | 常规：比较本地/远端相对基线的变化（见 4.3） |

说明（删除意图生命周期，审计第三轮条件 2）：本地「彻底删除意图」用本机标记（现有 deleted_notes/purged 状态）表达，**只在本地、不上云**。清除条件唯一为：**看到 generation 更大的索引且该 id 明确不在其中**（证明删除已传播且不会被迟到覆盖）；**显式 restore 是唯一的提前清除条件**。发布成功本身不构成清除理由。无基线（download-only）时删除意图**休眠但保留**，不得清除。

### 4.3 常规条目的三种情况

- 本地 hash ≠ 基线、远端 hash == 基线 → 上传本地（先扫描本地附件、写资产声明与正文）。
- 本地 hash == 基线、远端 hash ≠ 基线 → 下载远端（含附件声明差集）。
- 两边都 ≠ 基线 → **远端胜**（先提交者已发布）；本地当前版本强制写历史快照并提示「已被覆盖」；后续以远端为基线。
- 元数据（标题/父级/排序/图标/锁/kind）独立用 `updatedAt`（锁用 `lockedAt`）做字段级 LWW，不跟正文 hash 绑。
- 回收站标记（trashedAt / deletedFromParentId）也按 LWW 合并；恢复时写 restore_pending，本轮强制 active 并上传。
- **资产扫描失败不变量**：某篇资产扫描失败 → 该篇**不发布新声明**（保留旧声明）、不 markSynced、下轮重扫；绝不发布裁剪后的 assets 声明（否则他端缺图永久化，还会把在用附件送进待删队列）。

### 4.4 目录（folders）

规则与文档同构：absence = 删除；目录彻底删除 = 索引移除 + 子树的文档按各自规则处理（进回收站/purge）。不再需要 `folder.deleted` 字段。

### 4.5 小记

- 独立索引、独立正文/图片声明，但**同一次同步、同一次发布、同一个指针提交**（一次 pointer 写同时切换 lake / 小记；v3.1 再加标签第三空间）。
- 条目字段含 `assetsHash`（图片声明不可变版本的引用，缺省=无图）；删除 = 条目从索引消失；没有回收站，设备按基线推断（本地有、云端无 → 删除本地）。
- 标签（v3）：目录 + 条目 tagIds/tagsUpdatedAt 都在**小记索引**里（唯一真相源，与 261024 现状同构）；标签删除 = 目录缺席 + 关系移除，设备按基线推断。独立标签空间是 v3.1 的事（§13，本次不实现）。

## 5. 永久删除：零痕迹

### 5.1 彻底删除一篇文档时，当轮必须删掉

1. 全局索引里的条目（新索引不含 id）；
2. 该文档所有正文对象：按前缀 `objects/{noteId}-` 删除（含历史版本残留）；
3. 该文档全部附件：按前缀 `assets/{noteId}/` 删除；
4. 该 id 的全部资产声明版本：`meta/assets/{noteId}/`（含历史版本）；
5. 旧索引对象（指针切换后）。
6. **小记同构**：小记条目删除 = 索引移除 + `.qnote` 正文对象 + `quick-notes/assets/{id}/` + `quick-notes/meta/assets/{id}/` 全部声明版本。

**顺序**：先发布新索引与指针（世界状态里已经没有它），再删对象；删除失败进入本地待删队列，下轮继续。**待删键必须在发布之前就持久化（先入队、后发布）**——否则指针写成功后的崩溃会让这些键彻底丢失（审计 P1）。这样最坏情况只是「短时间内还有孤儿对象」，**不会永久留痕**。删除执行必须经 §5.2 的**执行门禁**（审计二轮 R1）。

### 5.2 待删队列（本地）

- **写入时刻是硬约束**：§3 第 7 步计算完、**发布之前**批量写入本地表；队列项至少记录 `key/prefix`、删除类型、`epoch`、目标 `generation`、目标 `commit`、创建时间（审计第二份 P1-B）。删除成功后出队。这样任何时点的崩溃，下一轮都会从队列续删。
- **执行门禁是硬性规则（审计二轮 R1）**：待删队列中的任何键，只有以**执行时刻**（不是入队时刻）的当前世界状态校验「已不再被引用」才允许删除；仍被引用 → **跳过删除并出队**（不是保留）。世界状态 = 当前指针指向的索引 + 索引条目 contentHash 对应的正文对象 + 各篇资产声明。按键型：

| 键型 | 门禁条件 |
|---|---|
| `objects/{id}-{oldHash}.lake`（被替换旧正文） | 当前索引中该 id 条目不存在，或其 contentHash ≠ oldHash |
| `assets/{id}/{filename}`（被移除附件） | 当前索引该 id 的 `assetsHash` 对应声明不含该 filename（缺省视为不含） |
| `meta/assets/{id}/{oldDeclHash}.json`（旧声明版本） | 当前索引该 id 的 `assetsHash` ≠ oldDeclHash（或该 id 不存在） |
| purge 前缀键 `objects/{id}-*`、`assets/{id}/`、`meta/assets/{id}/` | 当前索引不含 id |
| `quick-notes/meta/assets/{id}/{oldDeclHash}.json` | 小记索引该 id 的 `assetsHash` ≠ oldDeclHash（或该 id 不存在） |
| 小记 purge 前缀 `quick-notes/objects/{hash}.qnote`、`quick-notes/assets/{id}/`、`quick-notes/meta/assets/{id}/` | 小记索引不含该 id |
| 旧索引对象 `meta/index/{oldHash}.json` | 当前指针对应空间的 commit ≠ oldHash |

- **仍被引用 → 出队**的理由：引用仍在只有两种成因——(a) 该键对应的发布从未发生（崩溃在入队后、发布前），本地删除/编辑意图仍在，下次成功发布会重新计算并重新入队；(b) 他端恢复胜出、重新发布了引用，本端删除意图应当作废。两种成因的正确动作都是放弃本次删除；**出队是唯一安全动作，保留会让这个洞在未来某轮重新打开**。
- **与现状同构**：这正是现行 `runGcReconcile` 的既有语义（`electron/s3Maintenance.ts:110-119`：「已过窗口 ∧ 不在 keep → 删除；已过窗口 ∧ 在 keep → 清表不删」）。v3 只是把「全局 keep 集」换成「当前指针 + 索引 + 资产声明」。
- **残余窗口（诚实披露）**：门禁校验与 `deleteMany` 之间存在毫秒~秒级 TOCTOU（他端恰好恢复并发布）。后果：恢复端本地副本仍在、云端缺对象、hash 一致无人重传。单人 2~3 设备可接受；v3.1 可选加固：下载侧遇「索引引用的对象 404 且本机 hash 匹配」时补传一次（现状「本地缺正文从云端拉回」的对称操作）。定位：**删除只是回收，不是正确性的前提**；世界状态由指针+索引定义，孤儿无害，缺对象靠警告暴露。

- 每轮同步开头/结尾各重试一次；连续失败超过阈值时在资源页提示用户。
- 可选「深度清理」按钮：列举 `objects/`、`assets/`、`meta/assets/`，与当前索引比对，删除未引用对象（用于崩溃/半途失败的兜底；2 万/20 万规模下这是秒级到分钟级操作，不进日常同步）。**深度清理必须走与 §5.2 相同的执行门禁**：只删「当前索引 + 当前声明均不可达」的对象，不得绕过。

### 5.3 不会进云的东西（永久不留痕）

- 历史快照、回收站内容的本地副本、被覆盖版本的正文（上传前就被本地历史接管）；
- 设备本地视图（缩放/选区/工作表/多维表导航）；
- 删除前内容的云端副本（墓碑取消）；
- 旧索引/提交链（只保留当前一份）；
- 迁移期的旧清单对象（迁移完成后删除）。

### 5.4 回收站与自动过期

- 软删（回收站）条目仍在索引里，附件仍保留 —— 这是「未真正删除」，不是痕迹。
- 本地自动过期（默认 60 天）触发彻底删除，走 5.1 流程；云端不留任何东西。
### 5.5 「零痕迹」的边界与部署要求（审计第二份 N3）

- **承诺收窄为**：在指定 bucket/prefix 的**应用可见对象**中，purge 完成且待删队列清空后，不再存在条目、正文、附件、声明、旧索引或应用可读取的删除元数据。
- **应用不可控、按第三轮复核最终口径分类**：
  - **部署前置约束**（启用则预检失败，或用户明确取消「零痕迹」承诺）：bucket versioning（旧版本与 delete marker）、object lock / WORM / 合规保留、跨区域复制副本；
  - **应用负责清理**：multipart 上传中止后的残留；发布窗口内新旧索引短暂并存（最终一致）；同步/GC 失败日志中的 key/id/hash；
  - **范围外**：服务端访问/审计/计费日志。
- **实施要求**：部署前检查并关闭 versioning/object lock/replication（或用户明确接受）；multipart 中止后清理；日志保留策略由用户确认；零痕迹验收断言只在待删队列清空后执行。
- **261025 实测（当前桶）**：GetBucketVersioning / GetBucketReplication 返回 501 NotImplemented，Object Lock 配置不存在（404），multipart 中止后可清理 → 当前桶满足部署约束；**换桶/换 provider 必须复测**（§6.7）。
- 若要求**服务商层面字面零痕迹**，超出应用范围，需要单独评估（不列为 v3 承诺）。


## 6. 并发、锁与故障

### 6.1 锁只覆盖发布窗口

- 对象：`meta/lock.json`（普通对象，S3 足够）。内容 `{ deviceId, time, ttl: 120 }`。**锁只是协作性提示，不是互斥保证**：261025 真云实测并发抢锁 20/20 双持（无原子条件写）。正确性依赖 §6.6 的「读回 + 重试 + 持久删除意图 + 分叉检测」。
- **只在发布窗口取锁**（写 index 之后、写 pointer 之前），不覆盖整轮下载/上传：
  1. 读锁；不存在或已过期 → 写自己的锁 → 再读确认仍是自己（防同时抢）；
  2. 再读 pointer：commit 必须仍等于本轮开始时读到的值；不等 → 放锁，回到合并步重做；
  3. 写 pointer → 删除锁。
  4. CAS 重做设上界：连续失败 3 次则报错退出（下轮再来），避免两端互发变更时无限循环。
- 为什么不用整轮锁：需要串行的是**两次发布**（指针覆盖），不是下载/上传（内容寻址、天然幂等）。锁缩到发布窗口后通常只持有 1–2 秒，两台设备同时同步也很少撞上。
- 锁被占用：等 3–5 秒重试一次，仍占用则报错「另一台设备正在发布同步，请稍后重试」。绝不无锁写 pointer。
- 初始化 epoch 也要走同一把锁（防止两台全新设备同时初始化产生两个 epoch）。
- 极端情况（两端同时写 pointer）：pointer 是单对象覆盖写，最后一个胜。发布后必须**读回 pointer**：不是自己写的 → 视为本轮发布失败，按最新世界重合并、有限次重试后报错；配合 §6.6 的持久删除意图与分叉检测，正常编辑的丢失只会变成「回收站/历史中的旧版本」，不会静默丢内容；purge 复活风险见 §6.6 限制。

### 6.2 为什么要「写前再读一次」

- 锁有 TTL，网络分区时可能两个设备都认为自己持有；发布前再读 pointer 相当于一次「乐观 CAS」：基于旧 commit 的发布一律作废重做。
- 这一步是防「静默覆盖」的最后一道闸；没有它，在「缺席=删除」的模型里，被覆盖的条目会被其他设备读成删除。

### 6.3 崩溃窗口

- 对象写完、索引未写 → 孤儿对象，由待删队列/深度清理回收；世界状态不变。
- 索引写完、指针未写 → 孤儿索引，指针仍指旧状态；旧状态仍自洽（因为新索引只是候选）。
- 指针写完、基线未写 → 下轮按旧基线重新对比：已下载/已上传的对象内容寻址幂等；删除项已在待删队列。
- 指针写成功但删除未做 → 待删队列下轮补删；补删前必须过 §5.2 执行门禁（仍被引用则跳过并出队）。
- 下载过程中遇到对象不存在（远端刚删除）→ 跳过该对象并重读指针，本轮按新索引重做；不覆盖本地已有内容。

### 6.4 长期离线 / 基线丢失

- 有基线：长期离线回来，按三方对比：云端缺席 = 删除；云端新增 = 下载；本地改动照常合并。**不会误删、不会复活。**
- 无基线（重装/清数据/旧备份导入）：当新设备，全量拉取；本地数据不自动上推，需用户显式「导入」。
- epoch 变化：用户二选一（全量重拉 / 重新上传）。

### 6.5 与现有互斥域的关系

- v3 同步仍在现有**维护域串行队列**内执行（AGENTS §4 的 I1/I3）：网络往返不持写域，同域串行、禁止嵌套。
- v3 只替换「清单格式与删除推断」，不改变写域/维护域/高优先域的划分；小记单条推送仍走高优先域。
### 6.6 发布原语与「迟到覆盖」（审计第二份 N2）

- **锁不是 CAS**：读锁 → 写锁 → 再读确认不是原子操作；网络延迟/时钟偏移下两端仍可能同时认为自己持锁。锁只降低碰撞概率，**不能作为正确性保证**。
- **危险序列**：A purge X 发布并推进基线 → B 基于旧索引迟到发布把 X 写回 → A 下轮看到「远端有、基线无」按新增下载 → **已彻底删除的文档复活**。这违反删除压编辑、先提交者胜、零痕迹。
- **处置顺序**：
  1. **首选**：真云验证并启用条件写（`If-Match` / `If-None-Match` / 条件 Copy）发布 pointer；支持则锁只做碰撞避免。
  2. **无条件写**：增加**持久本地删除意图**（id + 删除代际）；清除条件唯一为「看到 generation 更大的索引且该 id 明确不在其中」，显式 restore 是唯一提前清除条件；无基线时休眠但保留。配合 §2.1 的「同 generation 不同 commit = 分叉」检测：迟到覆盖被发现 → 按删除意图重新压制并重新发布删除，绝不把 X 当新增下载。
  - **限制（必须写进承诺）**：持久删除意图依赖删除设备**本地状态仍在**；若该设备数据丢失/重装，迟到覆盖仍可能复活已删文档。要消除这一残余，只能依赖条件写（`If-Match` 等）；这是「无条件下写」的已知上限。
  3. **两者都不做**：必须明确承认存在极低概率违反硬语义，不能再写「语义与结果不变」（默认不选）。
### 6.7 条件写探测结果（261025 真云实测）

> 脚本：`scripts/s3-v3-probe.mjs`（只读环境变量，无密钥入库）；bucket `local-lake-hebei`，prefix `lake-notes-dev1`，报告 `/tmp/s3v3-probe-report.json`。

| 测试 | 结果 | 判定 |
|---|---|---|
| 覆盖写后立即读（30 轮） | 30/30 一致，最大 221ms | 读后写一致 ✓ |
| PUT `If-None-Match: *`（键已存在） | 写入成功（头被忽略） | **不支持条件写** |
| PUT `If-Match`（错误 ETag） | 写入成功（头被忽略） | **不支持条件写** |
| 并发抢锁（`If-None-Match:*`，20 轮） | 双持 20/20 | 锁不能互斥 |
| PUT 后 LIST | 即时可见 | ✓ |
| DeleteObjects 批量（10 键） | 成功、0 错误 | ✓ |
| GetBucketVersioning | 501 NotImplemented | 无版本化痕迹（部署约束满足） |
| GetObjectLockConfiguration | 404 不存在 | 无 Object Lock |
| GetBucketReplication | 501 NotImplemented | 无跨区复制 |
| Multipart 中止残留 | 1 → 0 | 应用可清理 ✓ |
| 探测键清理 | 0 残留 | ✓ |

**结论**：当前 Kodo 桶**不支持条件写**，因此 v3 **采用分支 2**（持久删除意图 + 分叉检测 + 发布后读回/重试），不采用分支 1；残余限制见下方「限制（必须写进承诺）」。真云实验在**迁移上云前**仍需在最终桶/region 复测一次（含 LIST 延迟、限流、multipart）。


### 6.8 Provider 可移植性与能力探测（阿里云/腾讯云/任意 S3 兼容）

**v3 的 fallback 路线只要求最基础的对象存储 API**，因此天然跨 provider；「条件写」只是可选加速。

| 能力 | 路线是否必需 | 说明 |
|---|---|---|
| PUT / GET / LIST / DeleteObjects | 必需 | 所有 S3 兼容 provider 都有；DeleteObjects 注意单批上限（逐批 ≤1000） |
| 覆盖写后立即读（read-after-write） | 必需 | pointer 读回校验、索引切换依赖；现代对象存储通常强一致，但网关/代理类需实测 |
| 覆盖写 + 幂等 | 必需 | 内容寻址对象、pointer 覆盖写 |
| Multipart 中止清理 | 必需 | 大附件中断后的残留清理 |
| 无 versioning / object lock / replication | 强烈建议 | 否则「应用可见零痕迹」之外仍有服务端痕迹；启用则部署预检失败或明确取消承诺（§5.5） |
| 条件写（`If-Match` / `If-None-Match`） | **可选**（有则升级） | 支持 → 走 CAS 分支（锁降级为碰撞避免）；不支持 → 持久删除意图 + 分叉检测（§6.6） |
| path-style / virtual-host | 配置项 | 移动端现有约束固定 virtual-host（AGENTS 已定），自建 MinIO 等需 path-style 的场景仅桌面支持 |

**能力探测（初始化 / 换桶时做一次，结果缓存本机并在设置页可见）**：
- 条件写：PUT 已存在键带 `If-None-Match:*` 是否被拒；PUT 带错误 `If-Match` 是否被拒（两者都被拒才算支持）。
- 一致性：覆盖写后立即 GET 是否读到新值；PUT 后立即 LIST 是否可见。
- 能力项：`conditionalWrite`、`readAfterWrite`、`listAfterWrite`、`deleteManyLimit`、`versioning`、`objectLock`、`replication`、`multipartAbortClean`。
- 一键脚本：`scripts/s3-v3-probe.mjs`（已入库，环境变量传凭证，不落盘密钥）；换 provider/换 bucket 必须复测并归档报告。

**已知 provider 备注（除七牛外均未实测，标「待探测」）**：
- 七牛 Kodo：261025 实测无条件写、无 versioning/replication、无 object lock、multipart 可清理（§6.7）。
- AWS S3：新版本支持条件写（`If-None-Match`/`If-Match`）；versioning 可能默认关闭，需部署检查。
- 阿里云 OSS：S3 兼容接口可用性/条件写/一致性需用本脚本实测；OSS 自有 API 与 S3 兼容层行为可能不同。
- 腾讯云 COS：S3 兼容接口较完整，条件写/一致性待探测。
- MinIO / Cloudflare R2 / Backblaze B2：S3 兼容，条件写与一致性随版本/网关而变，全部「待探测」。

**跨 provider 迁移**：等于换云端世界 → 走 §15 的 epoch/全量重拉或重新上传；正文/附件布局不变，不重传字节（全量重拉口径见 §15）。

## 8. 升级策略（261026 定稿：**不迁移**）

> 定稿口径：**不迁移、不读旧 manifest、不删旧数据**。旧 `manifests/latest.json` 只是留在桶里的孤儿；`electron/s3v3/migrate.ts` 一次性迁移工具与本节的「迁移」条目已删除（git 可查），不要再复活。

1. **升级 = 换客户端**：所有设备直接升级到 v3 版本即可，没有迁移步骤、没有升级顺序要求、没有「首个设备执行迁移」。
2. **首开 v3（新设备/旧库都算）= 从本地真相全量上传**：云端无 `meta/pointer.json` ⇒ 默认 `onEmptyCloud:"upload"`，读写 `objects/` 与 `assets/`（布局与旧协议相同，字节不重传，只补缺失对象）；随后写索引 + pointer 建立 epoch。
3. **旧 manifest 不读不删**：v3 完全不解析 `manifests/*`；旧对象既不进入 v3 索引，也不被 v3 引用/清理（成为孤儿；要清理由用户/运维自行处理）。
4. **不做历史回填/兼容**：与 AGENTS §3#7 一致；旧设备/旧版本客户端不在支持矩阵内。
5. **回滚**：换回旧版本客户端即可（旧 manifest 仍在，见 docs/S3-V3-CUTOVER.md §3）；v3 期间的新编辑会在旧通道下一次同步时重新上传到旧 manifest；v3 pointer 不动。**不提供应用内回滚开关**。
6. **同批修订长期红线（审计 P9，已完成）**：AGENTS.md §1（规模 2 万/20 万）、§3 #3/#5/#11/#13/#15（删除=缺席/无云端内容副本/每文档资产声明/并发 12/purge 清引用）已随 v3 同批改写。

## 9. 验收与测试计划

- **决策表全量单测**：4.2 的 7 种组合 + 4.3 的 3 种变化 + 回收站/恢复/purge/小记。
- **场景 e2e（双端，隔离 userData）**：新建/编辑/改名/移动/排序/锁/图标/回收站/恢复/彻底删除；A 删 B 离线编辑；B 先发布 A 后删；双端同时同步（锁）；崩溃三个窗口；epoch 重置；空云端；新设备全量拉取。

- **零痕迹审计**：purge 后列举 `objects/{id}-`、`assets/{id}/`、`meta/assets/{id}.json` 必须为空，索引中无该 id；覆盖旧版本、移除附件、删除标签后同样断言。
- **体积/传输基线**：合成 2 万文档 + 20 万附件，断言索引 <10MB、零变更请求数 =1、变更轮传输符合预算。
- **不迁移口径验证**：旧 `manifests/latest.json` 在首开 v3 后原样存在（不读不删）；首开只上传本地真相并建 baseline；旧对象成孤儿、不被 v3 引用；第二设备首拉字节≈索引+缺失对象，不是旧清单全量。
- **待删门禁断言（审计二轮 R1）**：第 7 步入队后、发布前崩溃 → 下一轮队列键被门禁全部跳过并出队，云端对象完好；本地下轮重新发布后重新入队并成功删除。restore-wins 竞态：A purge 入队后 B 恢复发布 → A 门禁判定仍被引用 → 跳过出队，B 恢复的副本不被删。
- **第三轮复核新增断言**：① **小记图片声明**同样不可变：替换后崩溃在 pointer 前，其他设备仍读到旧正文配旧声明（不混搭）；② 删除意图生命周期：发布成功后不清除；只有「更高 generation 且索引不含该 id」或显式 restore 才清除；无基线时休眠保留；设备数据丢失的复活风险按 §6.6 限制接受/靠条件写消除。
- **第二份审计新增断言**：① 资产声明替换时崩溃在「声明写入后、pointer 前」→ 其他设备仍读到旧正文配旧声明（不可变版本保证），不出现正文/声明混搭；② 迟到 pointer 覆盖已 purge 文档 → 分叉检测 + 持久删除意图压制，不复活；③ 同 generation 不同 commit → 进入修复流程而非增量删除；④ 小记 base 无 / local 有 / remote 无 → 必须上传（不得判删）；⑤ 深度清理不得删仍可达对象；⑥ versioning / object lock / replication / multipart 边界按 §5.5 部署检查。
- **专项单测/e2e（审计新增）**：① 待删键「先入队后发布」+ 指针写后崩溃（下一轮续删）；② 小记单条推送（v3 两空间）不被覆盖、不进完整同步；③ 无基线设备 download-only 硬闸；④ restore_pending 优先于缺席删除；⑤ 资产扫描失败不发布裁剪声明、不 markSynced。

## 12. 与旧方案详细对比（2 万文档 / 20 万附件）

| 维度 | 旧方案 | 新方案 |
|---|---|---|
| 本地新增状态 | 每篇一条 sync_base hash 账本 + 墓碑表 | 一份索引基线快照（约 3MB gzip，含两空间；标签 v3.1 才有第三份） |
| 零变更同步流量 | 约 14MB 下载 + 解析 34MB | 约 200B（1 次 GET） |
| 变更轮流量 | 约 14MB 下载 + 约 28MB 上传（commit + latest） | 约 3MB 下载 + 增量（通常几百 KB–几 MB） |
| 云端常驻元数据 | 5 份完整清单约 70MB gzip + 墓碑 | 1 份索引约 3MB + 资产声明约 10–15MB gzip（分散） |
| 永久删除后的痕迹 | 墓碑 + 删除前正文/图片永久保留 | **当轮清空，零痕迹** |
| 跨端恢复删除前内容 | 他端本地 purged 副本可恢复；云端内容仅遗留数据可能有 | 他端本地 purged 副本仍可恢复；云端不再有任何痕迹 |
| 并发 | 无锁，后写覆盖 + 下轮自愈 | 发布窗口锁 + 写前读回校验 |
| 同步层复杂度 | 整份重建 / 墓碑 / 全局 GC keep 集 / 提交链 / 双份写 / 记账 | 基线对比 / 发布锁 / epoch / 待删队列（机制更少、更局部） |
| 同步层代码量 | 现状 | **机制更少、长期更易维护；首版代码量大概率净增**（+迁移/基线/锁/待删队列，以及全部 latest.json 外围调用方改造）。原「-25%~-35%」是无依据估算，已撤回 |
| 迁移成本 | 无 | 一次性迁移（不重传正文/附件）+ 全设备升级 |
| 崩溃恢复 | 提交链 + 记账自愈 | 先对象后指针 + 待删队列 + 深度清理 |
| 可解释性 | 难讲清楚（清单/墓碑/链） | 一句话：云端只存当前状态，设备记上次状态 |

### 12.1 旧方案优缺点
- 优点：已经实现并稳定；他端本地保留 purged 副本可恢复；无锁、单写者模型简单；语义经过验证。
- 缺点：清单随库增长（2 万/20 万时每轮约 14MB）；零变更也全量传；墓碑与旧版本永久留痕；提交链 5 份；20MB 上限是悬着的硬伤。

### 12.2 新方案优缺点
- 优点：零变更几乎零流量；变更流量大幅下降；**永久删除零痕迹**；没有墓碑/链/全局 keep 集；规模封顶明确（2 万/20 万）。
- 缺点：需要迁移与全设备升级；云端不再留任何删除痕迹（仅本机/他端本地副本可恢复）；基线成为关键设备状态（丢失按新设备处理）；增加发布锁/epoch/待删队列三个新概念；深度清理需要新入口。

### 12.3 结论
对「2 万文档 / 20 万附件 + 永久删除零痕迹」这个目标，新方案更合适：**机制更少、长期更易维护**，但首版代码量大概率净增；主要成本是一次性迁移与双端验收，不是日常运行。

## 13. 标签空间（v3.1 设计，本次不实现）

> **v3 的定稿（唯一真相源）**：标签目录与关系继续放在**小记索引**里（与 261024 现状同构，迁移成本最低）。本节是「未来一套标签打小记 + 文档」的预留设计，v3 不落地；落地时必须把标签从小记索引移出，不能两处并存（审计 P5）。

- **第三份索引**：`meta/tags/{hash}.json`；`pointer.tags.commit`。一次 pointer 写原子切换 lake / 小记 / 标签三个空间。
- **结构**：`{ tags: [{id, name, color, order, createdAt, updatedAt}], links: [{tagId, targetType: note | quickNote, targetId, updatedAt}] }`。
- **删除 = 缺席**：标签删除 = 目录移除 + 相关 links 移除；设备基线推断，云端不留墓碑。
- **冲突**：目录按 updatedAt LWW；links 按 updatedAt 字段级 LWW（同一对关系后写胜）。
- **清理**：文档或小记彻底删除时，在同一个提交里移除其 links（原子、不会悬空）；标签删除同轮清 links。
- **为什么独立空间**：标签可同时打给两种实体；后续改标签规则（颜色/层级/批量）不用动文档索引；体积很小（通常 <1MB），不增加上限压力。
- **本地**：统一 tags 表 + links 表；搜索/筛选本地做，云端只镜像。
- **迁移**：把现有小记标签目录与关系一次性转成 tags 空间（targetType=quickNote）；文档侧入口后续再开。
- **不变量**：tagId 全局唯一；targetType 枚举稳定；links 主键 (tagId, targetType, targetId)。

## 14. 本次疑问的答复（对应你的 7 问）

1. **本地是不是有一份上次同步的云端清单？** 是。只存**元数据索引**（约 3MB gzip），不含资产明细；资产声明需要时按文档向云端取。
2. **加锁防什么？有必要吗？** 防两次发布互相覆盖指针。因为新模型里「云端没有 = 删除」，被覆盖会表现为**文档莫名进回收站**。所以有必要，但**只锁发布窗口（1–2 秒）**，不覆盖整轮同步；撞锁概率很低。
3. **删除进回收站 = 移动到回收站笔记本，和「删除不跨端」矛盾吗？** 对，表象就是「移动到回收站笔记本」：实现上把 parentId 改到回收站笔记本 + 记 trashedAt 与原父级，条目仍是正常条目，跨端可见/可恢复/可自动过期。**只有彻底删除**（清空回收站/自动过期）才从索引消失。云端现在本来也没有删除前内容（purge 先物理删正文再发占位墓碑），所以新方案去掉的是**墓碑元数据痕迹**，不是内容；曾同步过它的设备本地 purged 副本恢复能力保留。
4. **每次都要对一遍 index/assets 吗？** 不用。零变更只读 200B 指针；索引只在 commit 变了才读；资产声明只对「本轮变化或新下载」的文档取；全程不做 HEAD。
5. **复杂度/时间/流量？** 见第 12 节表：日常流量大幅下降（零变更 14MB → 200B），同步层机制更少；主要成本是一次性迁移与验收。
6. **标签空间怎么设计？** v3 **不拆**：标签仍在小记索引（唯一真相源，261024 现状）。未来统一标签（同时打小记+文档）用 §13 的第三份索引设计（v3.1），落地时把小记索引里的标签字段移出、link.updatedAt 作唯一时钟，不能两处并存。
7. **流程图和优缺点对比？** 见第 11、12 节。

## 15. 全量重拉 vs 重新上传（epoch 不一致时）

两者都是**单向、破坏性**的，必须二次确认 + 先做本地备份（DB + 正文目录）。一句话：**全量重拉 = 云端赢；重新上传 = 本地赢。**

| 维度 | 全量重拉（建议默认） | 重新上传 |
|---|---|---|
| 以谁为准 | 云端 | 本地 |
| 云端有、本地没有 | 下载到本地 | 视为本地删除 → 从云端索引移除 |
| 本地有、云端没有 | 不自动上传、不删除；移入「本地备份」区，可预览/可导入（见 §15.1） | 上传并加回索引 |
| 本地未同步的编辑 | 不进入同步（保留在本机历史/备份里） | 全部保留并推送 |
| 适用场景 | 云端被重置 / 换云 / 迁移后（云端是权威） | 确认云端数据作废、只用这台设备的数据 |
| 风险 | 本机未同步改动不会自动回来 | 覆盖云端，其他设备的数据可能被删（各设备本地副本还在） |
| 共同要求 | 强制本地备份 + 二次确认；绝不自动选择 | 同左 |

补充：迁移时会主动换新 epoch，所以其他设备第一次连上会走这条分支——默认全量重拉是安全的（云端由旧清单迁移而来，文档不会丢）。

同一 bucket 被从旧备份恢复（epoch 没变、generation 倒退）也走这条分支，不要当成普通删除。

**同 generation 不同 commit（分叉/迟到覆盖，N4）**：先查本地**持久删除意图**——若有，重新压制删除并重发（删除意图保留到看到 generation 更大的索引且不含该 id 才清除）；若无，走本节的「全量重拉 / 重新上传」二选一。绝不能把它当普通增量，否则迟到覆盖会让已 purge 文档复活（§6.6）。

**「全量重拉」的具体含义（审计 P7）**：= 重建本地基线 + 元数据对账；本地已有正文/附件按 contentHash 复用，**不重新下载字节**；「归档」只是给本地数据打「不参与自动同步」标记，**文件不移动**（用户可选择后续导入）。迁移后其他设备首同步的字节数应≈增量，而不是全库。

### 15.1 云端赢时，本地文档怎么办（不删、不传、进备份区）

**原则：云端赢 ≠ 删本地。** 全量重拉只换「当前库对应的云端世界」，本地多出来的数据**不自动上传、不静默删除**，而是进入「本地备份」区。按四类处理：

| 情况 | 处理 |
|---|---|
| 两边都有、内容相同 | 直接复用本地文件，用户无感（不重下） |
| 两边都有、本地改过 | **云端版本进当前库**；本地版本先写本地历史快照（现有 superseded 机制），可在历史里恢复 |
| 本地有、云端没有（本地新建 / 云端已删） | 移入**本地备份区**：仍可预览、搜索、删除；**不参与同步、不自动上传**。导入时默认**生成新文档（新 id）**，避免复活云端已删文档；高级选项「按原 id 上传」需二次确认（等于对该篇选择本地赢） |
| 云端有、本地没有 | 下载 |

本地回收站/小记里「云端没有」的条目，同样进备份区（保留原状态）。

**实现约束**：
- **文件不移动、不复制**（2 万/20 万规模下不做全库拷贝）：正文/附件原地保留，本地 DB 给这些行打 `archived` 标记 + 备份区列表；同步与 GC 必须排除 archived 行/文件。
- 确认页先展示统计：**云端 X 篇 / 本地 Y 篇 / 本地独有 Z 篇 / 本地改过 W 篇**，默认按钮「全量重拉」，破坏性操作二次确认，可取消。
- 不自动做：不上传、不删除本地文件、不覆盖本地历史。
- 反向的「重新上传（本地赢）」同理不物理删其他设备的本地数据：云端索引移除后，其他设备按缺席把本地副本移入各自回收站/历史。
- 迁移后常见情况：绝大多数本地数据云端都有 → 无感；只有「未同步过的新建/编辑」进备份区，用户可逐篇导入为新文档。

## 16. 与 git 的关系（是否参考 git 实现）

- **像 git**：内容寻址（blob）、对象不可变只写一次、指针/ref 指向状态、先写对象再写 ref、按可达性做 GC、用 lockfile 保护 ref 更新（git 的 index.lock 与我们的 `meta/lock.json` 同理）。索引大体相当于 git 的 tree（但只有一份）。
- **不像 git**：没有 commit DAG / parent 链 / 分支 / 历史；没有暂存区；一次同步只发布「最新状态」；冲突不合并（三方对比 + 先提交者胜 / 删除胜）；删除 = 缺席，不保留历史。所以它是「git 的一个子集：对象库 + ref + GC」，不是 git。
- **是否参考实现**：没有复用 git 代码或库。这套「对象库 + 指针 + GC」是通用做法，思源的 dejavu 也是同类思路；我们只借思想。
- **为什么不直接跑 git**：S3 上的 git 需要额外工具与大包对象；git 的历史 DAG 会重新引入「永久留痕」，与零痕迹目标冲突；同步语义也不同（我们不需要 merge/分支）。
- **借了哪些工程经验**：对象不可变只写一次；指针最后写；fsck 式深度清理（对应我们的「深度清理」）；ref 更新必须加锁（对应发布锁）；GC 只删「当前索引不可达且无待删记录」的对象。
