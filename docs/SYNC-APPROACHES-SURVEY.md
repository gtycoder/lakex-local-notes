# 同类软件怎么同步（261025 市场调研 · 大白话版）

> 用途：回答「为什么我们的同步这么复杂、别人怎么做的」。只看产品/逻辑，不含代码。
> 状态：调研文档，未改任何协议或代码。详细内部测算见 [S3-MANIFEST-SCALE-RESEARCH.md](./S3-MANIFEST-SCALE-RESEARCH.md)；墓碑专项对照见 [S3-GC-DESIGN.md](./S3-GC-DESIGN.md) 第 7 节。

## 0. 一句话结论

市面上的方案只有四种，**区别只在于「谁记住上次同步时云端有什么」**：

1. **记在每台设备本地**（Obsidian 的 Remotely Save 插件、Joplin、思源）——云端只存文件/条目，设备各自有一本小账本；
2. **记在服务端**（Obsidian 官方 Sync、Standard Notes、Notion）——需要一台服务器；
3. **记在内容里**（Anytype 这类 CRDT）——把合并逻辑做进数据本身；
4. **记在云端一份全局清单 + 永久墓碑**（**我们现在**）。

我们复杂，不是因为写错了，而是因为选了第 4 种：把「上次同步状态」放在云端一份大清单里，还要永久保留删除记录。别家把这个状态放在**设备本地的小账本**里，所以云端可以只是个网盘，心智简单得多。

## 1. 四派做法对照

| 派别 | 代表 | 云端存什么 | 删除怎么传 | 冲突怎么办 | 要服务端吗 | 代价 |
|---|---|---|---|---|---|---|
| 网盘镜像派 | Obsidian + Remotely Save（支持 S3）/ Syncthing / Git 插件 / Logseq | 就是文件树；没有全局清单 | 每台设备本地记「上次同步的文件映射 + 删除/重命名历史」，对比云端缺席来判断删除 | 生成冲突副本文件（两个都留） | 不要 | 没有「删除压编辑」；离线编辑可能复活；重命名有时被当成删除+新建；跨端排序/标签要另存小文件 |
| 条目数据库派 | **Joplin（原生支持 S3，官方标 Beta）** | 每条笔记/资源一个对象；S3 按文件系统驱动用 | 本地删除表只是待办队列，删完即销；远端删除靠「整桶列表里没有这个 key」推断，单轮变更量 >90% 时触发 fail-safe | 冲突 = 本地副本进 Conflict 笔记本；锁文件每端一把、**不互斥**，可并发同步 | 不要 | 每轮整桶 list（分页）；对象多则同步慢、请求多、S3 账单高 |
| 服务端条目派 | **Standard Notes**（必须自建服务端）、**Trilium(Next)**（需同步服务器） | 服务端数据库；S3 只放附件/导出 | Standard Notes：Item 带 deleted 软删标记（真墓碑行）；Trilium：entity_changes 增量 + isErased 墓碑**永久、从不回收** | 服务端或客户端按规则裁决 | 要 | 要维护服务端；Trilium 实测 1.2 万活实体对 16.5 万变更（≈85% 墓碑）——和我们的问题同款 |
| 快照索引派 | **思源（SiYuan/dejavu）** | 每次同步上传一份完整索引；旧索引按保留期清 | 删除 = 新索引里没有这篇；每台设备存一份「上次同步的索引」做对比 | 三方合并：本机改过就本地优先（可能复活删除） | 要云端锁（可以用 S3） | 索引全量读写、传输大；换机/长期离线要全量重拉；锁失败会提示稍后重试 |
| 服务端 / CRDT 派 | Obsidian 官方 Sync、Notion、Anytype、AppFlowy | 服务端数据库或 CRDT 操作日志 | 服务端说了算 / 算法自动合并 | 服务端或算法处理 | 要（或官方节点） | 不是纯 S3；要维护服务或依赖官方云 |

**没有免费午餐（实测数据）**：纯 S3 的 Joplin 牺牲了可靠性（删除靠列表推断，官方注释承认「删除列表要永久保存」却没做）；Trilium 干脆永久保留墓碑（≈85% 的记录都是墓碑）；Standard Notes 靠服务端才能软删 + GC；思源靠「全量索引 + 锁 + 保留期」。**四家都在为「删除」付代价，只是付在不同的地方。** 我们现在的问题不是「设计错了」，而是选了「可靠性」那一端。

### 关键事实：连最「简单」的网盘插件也要记删除

Obsidian 的 Remotely Save 在 S3 上同步时，并不是「无状态搬文件」。它的公开算法文档写得很直白：判断依据有四类——本地文件、远端文件、本地的删除/重命名历史、远端的删除历史；早期版本还专门往云端传过一个删除元数据文件（后来改成设备本地记录）。**也就是说：纯对象存储上，「远端没有这篇」永远有歧义，必须有东西记住「上次有什么」。** 区别只是记在哪里、多大、留多久。

## 2. 为什么到了我们这里显得复杂

行业里每家都只做**一个简化**，我们同时做了五个不简化：

1. **纯 S3，没有服务端**（不能靠服务端裁决）；
2. **云端一份全局清单**（为了不逐个文件探测，结果清单越写越大）；
3. **删除压编辑**（删除永远赢，离线编辑不能复活——所以删除记录必须永久保留）；
4. **树/排序/标签/锁/文档类型这些元数据在本地数据库里，不在正文文件里**（所以清单还得装下它们）；
5. **目标量级 10 万文档 / 100 万附件**（清单和「全量传输」都因此变得致命）。

单看每一条都合理；组合起来，就等于「用网盘当数据库用，而且没有裁判」。复杂度是这五个约束的必然产物，不是某段代码写坏了。

## 3. 三条「变简单」的路线（按心智模型命名）

### 路线 A：当网盘用（学 Remotely Save / Syncthing）
- 云端就是文件树：每条笔记一个文件，每个笔记本一个很短的索引（标题/顺序/标签）。
- 每台设备本地存一本「上次同步账本」；对比账本和云端 → 知道谁增删改；删除直接删云端文件。
- 冲突 = 冲突副本（两个都留），不自动合并。
- **得到一个非常简单的模型；失去「删除压编辑」**（离线编辑会把已删的带回来）。工作量：中。

### 路线 B：当数据库用（学 Joplin）
- 每条笔记/资源一个对象；每个笔记本一个小清单；删除记录是「小墓碑」；同步用锁文件协调。
- 保留「删除可靠」的语义；冲突仍然用副本解决。
- 代价：请求数多、同步可能变慢（我们 100 万附件会被放大）；需要做分页/增量。工作量：中。

### 路线 C：当快照用（学思源）
- 每次同步一份索引快照；每台设备存上次快照；云端锁；旧快照按保留期清。
- 语义最稳，也最接近「专业同步引擎」；代价是工程最大，且要接受「锁失败提示」「长期离线设备全量重拉」。工作量：大。

### 路线 D：维持现状 + 分片 + 锁/世代（我们调研文档里的方案）
- 保留现有语义，把大清单按笔记本切开，再加锁和云端世代；工程最大，但用户几乎无感。

## 4. 怎么选：先回答一个产品问题

**两台设备同时改同一篇文档，你要哪种结果？**

- **A. 各存一份冲突副本，谁都不丢**（Obsidian / Joplin 的做法）→ 选路线 A 或 B，复杂度立刻降一档；
- **B. 删除压编辑、不产生冲突副本，被覆盖的自动进历史**（我们现在的做法）→ 必须有「每台设备的基线 + 云端锁」，也就是路线 C 或 D；复杂度无法消除，只能收敛。

换句话说：**「简单」和「删除绝不复活」是互斥的**。现在的别扭感，来自我们既想要 A 的简单，又想要 B 的严格。

## 5. 建议

1. 先把「要冲突副本，还是删除压编辑」定下来——这一条决定路线，比任何技术细节都重要。
2. 如果选「冲突副本」：先在现有模型上做最小改动（分片前先做「每笔记本一个清单」），心智立刻简单；后续再评估是否彻底转网盘式。
3. 如果选「删除压编辑」：接受路线 C/D 的复杂度，但**用产品语言**对外表达为「每台设备记住上次同步状态 + 云端加锁」，不要再对用户讲清单字段。
4. 无论选哪条，**先做的都不是协议，而是给同步结果加「看得懂的解释」**：这次同步传了多少、为什么慢、删了哪些、冲突了哪些。
