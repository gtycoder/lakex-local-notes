## 四、CSP 收紧——明确搁置（未合并）

### 改动内容（3 文件一套）
- `index.html`：`script-src` 移除 `'unsafe-inline'` 与 `gw.alipayobjects.com`/`cdn.jsdelivr.net`；`connect-src` 从 `http: https:` 收窄为仅 `http://127.0.0.1:*`。
- `vite.config.ts`：新增 `cspScriptExtraPlugin()`，用 `__LAKE_CSP_SCRIPT_EXTRA__` 占位，dev 放行 `'unsafe-inline'`、生产替换为空。
- `public/vendor/lakex-doc/kitchen-url.js`：把 index.html 内联 `window.KITCHEN_URL` 抽成外部脚本（避免依赖 `unsafe-inline`）。

### 为什么搁置
1. **非刚需**：这是纯安全纵深防御，不影响功能；当前宽松 CSP 反而是 W-5 重定向未覆盖资源的兜底（CDN 直连"慢但能用"，收紧后"直接被拦坏"）。
2. **双刃剑**：`script-src` 不再放行 `gw.alipayobjects.com`，若 W-5 的 vendor 扫描漏掉资源（符号链接/大小写/启动未就绪），公式/图片将直接加载失败而不是变慢。
3. **需要配套验证**：若未来要合并，必须真实窗口打开含公式/思维导图/图片文档，确认：
   - DevTools Network 中 `gw.alipayobjects.com` 请求全部 302 → `127.0.0.1:19876`；
   - Console 无 CSP violation；
   - kitchen 图标正常（`kitchen-url.js` 生效）。
4. **不影响主进程同步**：S3 同步走主进程，不经过渲染层 CSP；IPC 已有 `isTrustedSenderFrame` 白名单，安全底线仍在。

### 后续决定点
- 若 W-5 覆盖完整验证通过 → 可单独合并 CSP 批并做真实窗口验证；
- 若 W-5 覆盖不完整 → 应给 W-5 加 `existsSync` 兜底（仅对未命中项），**而非收紧 CSP**。
