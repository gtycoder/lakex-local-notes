## P0（阻塞：数据丢失或核心功能错误，实现前必须解决）

### P0-1 恢复历史覆盖 .lake，会把"本地已改、远端未改"的修改变成新版本上传覆盖远端——违反既有冲突保护语义

**问题**
设计 §10 说"恢复后 sync_state='local' 重新上传"，但**只重置了 sync_state，没有重置 `sync_base`**。看 `sync.ts` 的冲突判定（syncNow 下载阶段）：

```
localChanged  = localHash !== null && localHash !== base  (base = sync_base.content_hash)
remoteChanged = rn.contentHash !== base
if (localChanged && remoteChanged) → 冲突副本
else if (localChanged) → 本地为准，上传
```

- 恢复写回旧版后，`contentHash` 变成"历史里的旧 hash"，而 `sync_base` 仍停在恢复前的 hash → `localChanged=true`。
- 若远端恰好在恢复前改过（remoteChanged 也 true）→ 产生"冲突副本"（安全但用户看到幽灵副本）。
- 更糟：若远端没改，**恢复的旧版会被当作"本地最新修改"直接上传覆盖远端**——A 设备用户后悔改错了、恢复旧版，把 B 设备（离线未同步过）的当前版永久覆盖，且 B 无感知。

**影响**
恢复操作会破坏既有同步冲突保护语义；多设备下 A 恢复旧版可直接覆盖 B 的新编辑（LWW 场景下最严重）。

**建议**
恢复动作**同时重置 `sync_base` 到恢复后正文的新 hash**（`setBaseHash(id, newHash)` + `markSynced`），让本地与远端进入"同一基线"。这样：远端同 hash → 双方一致；远端改过 → 正确判为远端变化，走既有下载/冲突路径。
注意：setBaseHash 必须用恢复后写盘内容的 hash（重新计算），不能沿用旧历史 hash 记录值。

### P0-2 `UNIQUE(note_id, content_hash)` 会让"历史回退→再次快照"永远去重失败，历史功能自身失效

**问题**
设计用 `{timestamp}-{contentHash}.lake.gz` 文件名 + `UNIQUE(note_id, content_hash)` 做"同内容不重复"。但内容 hash 只对**正文**去重，时间戳每次不同——回滚场景下：

1. t0 快照 A（正文 α）
2. t1 用户编辑到 β，快照 B
3. t2 用户"恢复 A"→ 正文变回 α，写盘
4. t3 定时器/手动快照 → 正文 α，**hash 与 A 相同 → INSERT 被 UNIQUE 约束/去重逻辑静默跳过**（历史里其实已有 A）

去重本身生效，但代价：
- **"恢复前先快照当前版本"（设计 §10 承诺）会失效**：当"当前版本 β"已经快照过 B 时，恢复前快照因 hash 相同被跳过 → 用户以为恢复有保护，实际**没有新增快照**，中间被覆盖的版本直接丢失。
- 无法区分"哪次恢复"，同一份 α 只保留最早一份。

**影响**
"恢复前留档"保护机制静默失效；历史去重与"每次恢复都留档"的语义冲突。

**建议**
- 去掉 UNIQUE 约束，去重改为"**同 hash 且在时间窗口内（如 24h）已有则跳过**"的防抖逻辑（防 15 分钟周期内同一内容连续写盘）。
- 或者保留 hash 列但**恢复动作强制写一条新快照（即使同 hash 允许重复）**，用 created_at 区分。
- 推荐：去掉 UNIQUE + 时间窗口防抖 + 恢复强制快照。

### P0-3 定期 15 分钟快照的"dirty 集合"仅存内存，崩溃/异常退出会丢失，漏快照无感知

**问题**
设计 §6 说"saveNote 成功时把 noteId 记入 dirty 集合"，定时器 15 分钟一轮，快照后清空。但：
- dirty 集合是**内存 Set**，无持久化。
- 应用在快照前**崩溃/被强杀**（断电、杀进程）→ 集合丢失，15 分钟内改过但没到周期的文档**永远漏快照**。
- 设计里的"启动兜底 cleanupHistory"**只是清理，不是补快照**——不会为"上次运行改过但未快照"的文档创建快照。
- 注意：macOS 关窗口≠退出（Electron-HANDOFF 坑 #16），退出钩子触发时机要对齐真正退出（before-quit）。

**影响**
崩溃场景下"防误改丢失"的历史保护出现真实空洞，且用户无感知。

**建议**
- dirty 集合**持久化**：`device_state` 存 `pending_history_snapshots`（JSON 数组），saveNote 成功后更新（可 15 分钟才刷盘一次，不必每次保存写 DB）。
- 定时器快照成功后清空并持久化。
- **启动时若集合非空，为其中文档补一次快照**（这同时满足"崩溃兜底"）。
- 至少：正常退出路径（before-quit）持久化一次。

## P1（重要：体验/一致性问题，建议实现时处理）

### P1-1 `restoreHistory` 写回后，打开中的编辑器 tab 与磁盘/DB 状态不同步，用户可能白恢复或再次覆盖

**问题**
历史面板恢复时，目标文档**很可能正开在编辑器 tab 里**（右键当前文档→历史→恢复）。恢复 IPC 只写磁盘 .lake + DB，渲染层 tab 的 `content` 状态和编辑器实例仍是恢复前的 β。之后：
- 用户继续输入 → contentchange → 800ms 后 `persistTab` 把 β 重新写盘，**恢复被静默覆盖**；
- 或 beforeunload 触发 `persistTab` 把 β 写回。

**影响**
恢复"看似成功、实则无效"，且无提示。这是比 P0-2 更常见的用户路径。

**建议**
- 恢复 IPC 返回后，前端必须**重新加载该 tab 内容**（把 tab.content 置为恢复后的 .lake，并重建/重置编辑器实例——注意锁状态与 EditorTab effect 依赖）。
- 最稳做法：恢复成功后**强制关闭并重开该 tab**（走 `openNote` 重新 `readNote`），或 `restoreHistory` 返回新正文、前端更新并触发编辑器 reload。
- 历史面板提示"若文档已打开将被重新加载"。

---

### P1-2 方案 A 与"打开中的编辑器/同步上传/导出正在使用的资源"存在真实竞态窗口

**问题**
自动清理（200份/45天）删快照后立即物理删资源；但资源可能正被：
- **打开中的编辑器/Viewer 引用**（用户正看着一张图，图片此刻不在"当前正文引用"里——例如用户刚删除正文里的图片还没保存，或正则漏判）；
- **同步上传进行中**：sync.ts 上传阶段读资源文件，删除与读并发 → ENOENT；跨 await 点（remote.put 之间）清理可能插进来，先删文件、随后 manifest 阶段仍把文件名列入 assets → 远端对象缺失，其他设备下载校验失败中止；
- **导出进行中**（exportNote 读资源）。

**影响**
多设备同步完整性受损（远端清单引用缺失对象）；编辑器内裂图；导出失败。设计完全没提这个并发窗口。

**建议**
- 清理动作与同步/导出共用一把**主进程锁**（syncInFlight 已有先例）：`cleanupHistory`/`cleanNoteOrphans` 执行时若同步/导出进行中则跳过或排队。
- 或更简单：资源物理删除延迟到"无活动编辑器引用"——前端 openTabs 中该 noteId 存在即跳过自动物理删（或仅标记不删）。
- 至少：物理删资源**逐个 try/catch + 删除失败保留记录可重试**（仿 cleanOrphanAssets 审计 #12），**先删 DB 引用后删文件**，保证重试安全。

### P1-3 `detectOrphans` 只按当前正文判孤儿，导致"被历史引用的资源"被全局清理物理删除、且从同步上传中消失

**问题**
设计说"detectOrphans 仍只按当前正文判定，不查历史；历史保护在清理动作时实时判定"。但 `orphan_assets` 表有两个消费者：
1. **同步上传**：sync.ts 用 orphans Set **跳过上传**孤儿 → 被历史引用的资源不上传 → **新设备拿不到历史需要的资源**，回滚裂图；
2. **SyncPanel 全局清理**：`cleanOrphanAssets` **物理删除**孤儿 → 用户顺手清理，历史回滚彻底裂图。

设计 §10 说"历史保护在清理动作时实时判定"——但**全局 `cleanOrphanAssets` 没有接历史保护**，文档级 `cleanNoteOrphans` 接了、全局没接，漏网。

**影响**
"历史资源不复制、靠引用保护"的核心机制在全局清理/同步两条路径上失效；多设备回滚必裂。

**建议（首选）**
**`detectOrphans` 判孤儿时把"该文档全部历史 refs"并入 protected 集合**：孤儿表只登记"当前正文不引用**且**历史不引用"的文件。这样全局清理、同步跳过、文档级清理三个消费者自动一致。历史查询低频 + 几十 ms，保存路径可接受（实测解压+解析 ~1.34ms/篇）。
备选：全局 `cleanOrphanAssets` 清理前逐条查历史 refs 跳过；同步上传时"孤儿但被历史引用"的资源仍上传。

### P1-4 自动清理的"物理删"发生在无 UI 确认的后台路径，用户误删历史后资源立即消失，且无任何反馈

**问题**
方案 A（已确认）的语义是"删历史快照 → 未引用资源立即物理删"。但**自动清理（200份/45天）也是方案 A**：用户没做任何操作，只是 45 天后/超 200 份，旧快照被删、资源被物理删。此时：
- 用户以为"我删快照只是删快照"，不知道资源也没了；
- 用户正开着历史面板看旧版本列表时，删到一半资源消失，预览裂图；
- 没有任何日志/通知说明"自动清理删了 X 个快照、释放 Y 个资源"。

**影响**
数据被后台静默删除，用户无感知、无解释。

**建议**
自动清理结果（删了多少快照、物理删了多少资源、释放字节数）**记录到 device_state 或返回 UI 提示**；历史面板/设置里显示"上次自动清理"摘要。至少加日志。

### P1-5 45 天兜底在"从不新建快照"的文档上永不触发；"启动兜底"是清理不是快照，触发机制与清理目标错配

**问题**
保留策略"200 份为主 + 45 天兜底"，触发点是"创建快照后（惰性）+ 启动兜底"。但：
- 文档一旦创建过快照，之后**用户不再编辑**（或只读/锁定不产生快照）→ 不会有新快照 → **惰性清理永不执行**；
- 启动兜底只在启动时执行，用户**一直不重启应用**（macOS 笔记本常开数月）→ 45 天兜底永不触发，历史目录无限挂老快照（磁盘缓慢膨胀）。
- 45 天兜底要清理的场景（旧快照无人碰）恰恰是"不会再有新快照"的场景，触发机制与清理目标错配。

**影响**
45 天兜底形同虚设；磁盘随老快照缓慢膨胀。

**建议**
兜底清理（45天+200份全量巡检）改为**独立定时器**（如每天一次 / 启动后 1 小时），不依赖"创建快照"事件。全量清理实测 62ms/1000 文档，每天一次成本可忽略。

### P1-6 恢复对"锁定文档"未定义：恢复覆盖只读文档正文与锁语义冲突；锁定切换重建期恢复会被编辑器覆盖

**问题**
- 锁定文档 = 只读保护，恢复历史**直接写盘覆盖**绕过了锁的保护语义（用户以为是安全只读，结果正文被换掉）。
- 更隐蔽：EditorTab 锁定切换会重建 Lake 实例，重建期间 `setting` 标志屏蔽 contentchange；若恢复恰好在重建窗口发生，前端旧内容可能在重建后 setDocument 把恢复结果覆盖。

**影响**
锁的语义被绕过；恢复结果在特定时序下失效。

**建议**
1. **锁定文档是否允许恢复**需明确。建议：恢复操作要求**解锁**（或恢复完成后保持锁定状态，但恢复时临时解锁写盘再重新加锁——注意重新加锁会触发 EditorTab 重建，时序要处理）；至少 UI 明确提示。
2. 恢复后若文档打开中，必须重载 tab（P1-1）。

### P1-7 删除/恢复回收站与历史生命周期完全脱节，会留下"幽灵历史"与孤儿资源

**问题**
- 文档进回收站（deleteTreeNode 软删）后，**历史快照和 history/{noteId}/ 目录还留着**；
- 恢复回收站（restoreTrashItem）→ 历史快照还在（好），但设计**没提恢复时对历史做任何处理**；
- 彻底删除（purgeTrashItem）→ 按设计保留"被历史引用的资源"——**但历史快照本身呢？** 如果 history/{noteId} 目录也删了，保留的资源变成无人引用的孤儿；如果历史目录留着，"彻底删除"就没删干净（磁盘泄漏），且该 noteId 若未来被新建（seed 用固定 id 如 welcome-note 可能复活）会继承别人的历史。
- 设计 §6"删除文档前快照"只覆盖了进回收站前；**恢复回收站后**要不要快照？没提。

**影响**
回收站生命周期与历史生命周期脱节：磁盘泄漏、幽灵历史、资源孤儿化。

**建议**
明确历史在回收站生命周期中的处理，推荐：
- **purgeTrashItem：连同 history/{noteId}/ 目录与 note_history 记录一并删除**（"彻底删除"就彻底，不留幽灵历史）。资源按 noteId 隔离，purge 后该文档历史删除即可全删资源——注意"保留被历史引用的资源"与"删除历史目录"二者只能选一个，否则自相矛盾。
- restoreTrashItem：**恢复成功后立即为恢复的文档建一条快照**（恢复前版本留档），成本低。
- 定期 scan `history/` 下无对应 note 的目录，清理孤儿历史目录。

## P2（建议：体验/健壮性打磨）

### P2-1 ref_count 列没有实际用途，徒增维护成本

**问题**
设计说 ref_count 是"轻量元数据，供未来统计/排序，不参与判定"。它**没有消费者**（判定只读 refs_json 合并），排序/统计用 refs_json 反序列化一样能算（快照列表最多 200 行）。多写一列 = 多一处一致性风险（refs_json 更新而 ref_count 忘更新）。

**建议**
**删掉 ref_count 列**（或作为派生字段由 refs_json 算，不出现在 schema）。若要保留，至少明确它的消费者是谁。

---

### P2-2 正则 `\d{13}_[0-9a-f]{8}\.(ext)` 的误判面比设计描述的更大

**问题**
除了"伪造相似文件名"，正文里任何巧合文本都会命中（用户写 `20260101120000_00000000.jpg` 这种文字、外部 URL 恰好长这样、代码示例）。真正的风险：
- **误判导致误保护**：磁盘上恰好有一个同模式文件但正文其实没引用它（用户手动放文件进 note-assets）→ refs 把它算作"被历史引用"→ 永远不清理；
- **漏判**：Lake 未来改资源命名（加 query、data URI 直嵌、大小写 ext、webp→heic）→ 全部失效且无感知（历史照常创建、refs 空，资源全靠"当前正文引用"保护，一删历史就物理删）。

**建议**
提取公共工具 `extractAssetRefs` 时（设计 §13 已计划）：
- **校验"文件名确实存在于该 note 的 note-assets 目录"再计入 refs**（扫描磁盘成本低，与资源管理语义一致）；
- 为命名模式留**版本化常量 + 单测**（命名模式变更时测试立即红）；
- 引用解析失败/为空时（大文档被截断、.lake 损坏）**跳过该快照创建并告警**，而不是静默存空 refs（空 refs 会让清理误删）。

---

### P2-3 全量清理/快照创建的阻塞成本在"主进程主线程"，极端情况会卡 UI

**问题**
实测 62ms/0.56s 是全量**纯内存**解析，但真实清理含：磁盘扫描 + gzip 解压 + 物理删除（fs.unlinkSync 同步）+ SQLite 写，0.56s 之外还有 IO；且这一切跑在 **main 进程 IPC 同步 handler**（ipcMain.handle 同步函数直接阻塞事件循环），0.5-1s 卡顿会冻结整个应用（含 assetServer 响应、同步、窗口事件）。

**建议**
- 快照创建：只 15 分钟一次，gzip+写盘+DB 一行事务（几 ms～几十 ms），同步可接受。
- 全量清理（含物理删资源）：**异步化**——IPC handler 返回 Promise，用 setImmediate/拆批（每删 50 个 yield 一次）或 Worker；至少 IPC 层 await，不长期阻塞主线程。
- 文档级孤儿列表/清理是用户主动低频操作，同步可接受。

---

### P2-4 快照的 created_at 与文件名时间戳建议统一来源，避免排序混乱

**问题**
文件名用 `YYYYMMDD-HHmmss`（本地时区），DB 用 ISO（UTC）。跨时区/手动改系统时间时，`ORDER BY created_at DESC` 与文件系统排序可能不一致；设计没规定恢复列表排序以谁为准。

**建议**
DB `created_at` 为唯一时间权威，文件名时间戳仅作可读标识；排序一律按 DB。

---

### P2-5 历史面板"删快照→立即重算孤儿"的时序：删除失败时孤儿列表要回滚刷新

**问题**
设计 §5 强调"删快照后立即重算孤儿"避免漏删，但若**删除快照成功、刷新孤儿失败**（IPC 错误/崩溃），UI 停留在旧孤儿列表，用户以为已清理——下次打开面板才会重算。

**建议**
实现时注意"刷新失败要给错误提示并保持可重试"；每次打开面板都 refresh（设计已提）。

---

### P2-6 磁盘增长缺少全局视图与用户可感知的清理入口

**问题**
200份×57KB≈11MB/文档，100 个活跃文档 ≈ 1.1GB（gzip 后实际更小），加上 45 天兜底多数文档会停在 ~200 份。单看可接受，但**用户无感知**：没有"历史占用磁盘 X"的展示，设置里"全部清理"又太极端。

**建议**
设置面板显示"历史占用量 + 快照总数"；提供"每文档上限"可配置（如 100/200/500）与"清理 45 天前"按钮。

---

## 结论：需修改后实现

设计整体扎实、决策记录清晰，性能实测和"refs_json 按快照记录 + 实时合并"的资源引用方案是对的，方向无需推翻。但有 **3 个 P0 必须解决**：

1. **恢复的同步语义**（P0-1）：恢复后必须重置 `sync_base`，否则恢复的旧版会以"本地最新修改"身份覆盖远端，破坏既有冲突保护——最严重的一处。
2. **hash 去重的回滚失效**（P0-2）：`UNIQUE(note_id, content_hash)` 会让"恢复前留档"在内容未变时被静默跳过，需改为按时间窗口防抖或恢复强制写快照。
3. **崩溃丢失 dirty 集合**（P0-3）：15 分钟快照的脏集合需要持久化 + 启动补快照，不能只做"启动清理兜底"。

P1 中至少应解决：恢复时打开 tab 的重载（P1-1）、自动清理与同步/导出的并发锁（P1-2）、**detectOrphans 判定孤儿时并入历史 refs**（P1-3，否则全局清理/同步上传两个消费者会漏保护）、回收站与历史的生命周期一致性（P1-7）、锁定文档恢复策略明确（P1-6）。P2 是打磨项。

**实现顺序调整建议**：把 §13 的顺序调整为**先做 P0-1/P0-2/P0-3 对应的表结构与恢复语义**，再按原顺序推进——这三个问题直接影响核心数据结构（note_history 的 UNIQUE 约束）和恢复函数的返回值设计（是否返回新正文/hash），越晚改成本越高。
