# 性能优化评估清单（供逐条分析）

> 状态：2026-08-15 隐藏回收站笔记本重构合并 master 后整理。
> 用途：列出"已做"与"建议待评估"的性能优化项，每条含现状/问题/方案/成本/风险，供逐条决策是否实施。
> 数据量假设：正式数据 ~9000 笔记 + ~1000 回收站条目（用户量级）。

## 0. 已落地的优化（无需再评估，验证通过）

| # | 项 | 效果 |
| --- | --- | --- |
| D1 | **零变更早退**：记录 lastSeenCommitId + 墓碑签名，远端未变且本地无 pending → 整轮跳过 | 零变更同步从 ~3-6s（10k 条）降到 ~200-500ms（只 connect + GET manifest 头 + 小记同步） |
| D2 | **下载 fast-path 记账去重**：批量读取 sync_base（替代逐条 lastSyncedMetaAt），已 synced 且 base/meta/锁一致 → 跳过 setBaseHash/markSynced | 10k 条零变更省 ~4 万次 DB 写 |

| D4 | **manifest gzip**（此前已做） | 实测体积 -87% |

## 1. 建议评估：增量 manifest（只传 diff）——最大单项，但工程量大

- **现状**：manifest 是"每端全量清单"（v4，含全部笔记+回收站条目）。**有变更**时每次同步仍要：下载 ~4MB gzip → JSON.parse + validateManifest（10k 条正则）→ 重写 → 上传 ~4MB gzip。10k 条估 **1-3s/次**（后台，不卡 UI，但带宽/电量有成本）。
- **问题**：O(N) 是协议固有成本，随数据量线性涨。9000 笔记的 manifest ~10-30MB raw / ~1-4MB gzip。
- **方案选项**：
  - A. **增量 manifest v5**：latest 只存 commitId + 变更条目，历史条目按需拉取（需要"完整清单缓存 + 重放/基线重建"）。彻底解决，但要改协议 + 迁移 + 兼容旧端。
  - B. **分段/分页 manifest**：按笔记本分片，只拉变更分片。折中，复杂度中等。
  - C. **保持现状**：接受有变更时 1-3s 后台同步（UI 不卡）。如果真实数据长期 < 2 万条，可能够用。
- **成本**：A 约数天（协议 + 迁移 + 双端兼容）；B 约 1-2 天。
- **建议**：先跑真实数据看单次同步耗时与用户感受；>2 万条或同步频繁再上 B/A。

## 2. 建议评估：validateManifest 校验成本

- **现状**：每次下载对每条 note/asset 做 `^[a-f0-9]{64}$` 等正则校验（10k 条 × 资源数）。
- **方案**：校验逻辑本身安全必要（远程不可信，审计 #19），可优化为"批量校验"（减少 per-item 分配）或在早退后彻底跳过（已做 D1）。**建议维持现状**，除非解析耗时实测显著。

## 3. 建议评估：GC 深度清理 / 对账

- **现状**：`runDeepCleanup` 列出 objects/assets/manifests 全量（可能几万对象）再逐批删；`runGcReconcile` 遍历 pending 表。默认 gcIntervalHours=24，后台执行。
- **方案**：若对象数大，可加分页 list（ListObjectsV2 已分页）+ 限制单次清理量/错峰。**建议维持现状**，量大再优化。

## 4. 建议评估：listTreeNodes 每次全树递归 CTE

- **现状**：每次渲染树/刷新都 `WITH RECURSIVE` 排除回收站子树，10k 节点每次都全扫。
- **方案**：树结构简单，SQLite 全扫 10k 行 < 20ms，可接受。若树大或频繁，可加"子树缓存/仅返回变更"。**建议维持现状**。

## 5. 建议评估：大文档 / 编辑器渲染（独立于同步）

- **现状**：1.37MB Lake 文档实测同步/打开正常；编辑器大文档渲染是前端（slate/drawnix）话题。
- **方案**：虚拟滚动、懒加载图片（渲染层），与本次重构无关。**另立专题**，不在本清单展开。

## 6. 建议评估：资源服务器 `?base64=1` 全文件读入内存

- **现状**：复制图片时 `fs.readFileSync` 整文件（≤25MiB）+ base64（约 +33%）。单图峰值 ~34MB。
- **方案**：上限已有（25MiB）；可流式/降级。**建议维持现状**（低频操作）。

## 7. 建议评估：自动同步频率与带宽

- **现状**：interval 模式默认 15 分钟一次；有变更时每次上传整份 manifest（~1-4MB gzip）。
- **方案**：可把 manifest 上传改为"仅当有变更"（已由 D1 早退覆盖零变更；有变更才传）。**已覆盖**。

## 8. 建议评估：历史快照在冲突/覆盖时读文件+hash

- **现状**：superseded 路径对每个被覆盖文档 createHistorySnapshot（读 .lake + hash + 写盘）。只发生在冲突/他端覆盖，低频。
- **方案**：24h 同 hash 去重已做。**建议维持现状**。

## 9. 观察项（暂不行动）

- 小记同步独立 manifest（小而稳，无需优化）。
- 单实例锁/并发队列已保证同步串行，无并发风险。
- 渲染层内存 8GB heap 上限（`--max-old-space-size=8192`）偏大，可在 Electron 42 升级时复查。
