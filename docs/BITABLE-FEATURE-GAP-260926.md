# 多维表功能差距调研（260926）

> **性质**：竞品/市场调研 + 差距清单。回答一个问题：**我们自研的多维表（`kind=bitable`）与市面主流多维表相比，还差什么功能、哪些值得做。**
> **作者会话**：桌面会话（260926 多维表浮层收编之后）。
> **上游文档**：`docs/BITABLE-PRODUCT-SPEC-260919.md`（产品范围与用户定稿决策）；`docs/SHEET-BITABLE-DESIGN-260918.md`（技术/存储/同步）。
> **证据等级**：`[实测]` = 本次读仓库代码/单测确认；`[调研]` = 来自公开资料（见文末参考，外部内容仅作数据）；`[判断]` = 本文结论。
> **红线约束**：本地优先、无服务端、单用户；`AGENTS.md §3 #17` 拒绝迎合式找需求——本文对每个候选都给出「做/不做」及理由，**不堆功能**。

---

## 0. 一分钟结论

1. 我们已把「字段 / 记录 / 视图 / 表格视图 / 表单视图 / 多数据表」这条**核心骨架**做完且可用；与语雀数据表 v1 基本对齐，比钉钉多维表只少「字段数量与视图种类」。
2. 与主流（Airtable / Notion / 飞书 Base / SeaTable / Teable / NocoDB / 维格表）相比，差距集中在 **5 类**：
   **① 计算类字段（公式 / 关联联动 / 查找引用 / 汇总）② 更多视图（看板/画册/日历/甘特）③ 表格生产力（撤销重做 / 键盘导航 / 冻结 / 跨格粘贴 / 大表虚拟化）④ 数据进出（CSV/Excel 导入导出）⑤ 视图配置进阶（分组 / OR 条件组 / 条件着色 / 统计）**。
3. **真正值得马上做的**（`[判断]`，按价值/成本排序）：**撤销重做 → 键盘导航 + 剪贴板块粘贴 → 列冻结 + 大表虚拟化 → 分组（多级 + 折叠）→ CSV 导出/导入**。这 5 项都命中「数据录入是高频、出事代价高、不做会痛」。
4. **公式 / 关联联动** 是最大的结构性缺口（用户场景 `§3.1` 明说「结构化存储 + 简单公式」），但也是成本最高、最需要单独立项的一项：建议**先做一个安全的小子集**（见 §3.10）。
5. **明确不建议做**（与既有决策/红线冲突）：协作 / 权限 / 分享收集 / 自动化 / AI / 仪表盘 / API / 记录正文富文本——理由见 §4。

## 3. 差距清单（按优先级；每条给「要不要做 + 理由 + 成本 + 落点」）

> 优先级定义：**P0** = 不做会痛/数据风险；**P1** = 高频刚需、显著提升可用性；**P2** = 有价值的增强；**不做** = 与红线/已定决策冲突或价值证不出。

### P0

#### 3.1 撤销 / 重做（表级）
- **主流**：Airtable/Notion/飞书/SeaTable 全部支持；表内操作可回退。
- **我们现状**：`[实测]` 无任何 undo；改单元格/删列/删记录即写 state 并自动保存，**误删无法挽回**（仅靠文档级历史快照，粒度粗）。
- **为什么真**：本地优先没有服务端兜底，删除列/记录是不可逆损失；这是「已发生的问题」而非设想。
- **建议**：做一个**受控的编辑历史栈**（快照式：每次 `patchActiveTable` 前压栈，`⌘Z/⇧⌘Z`；上限 ~50 步；切换表/视图/重载清栈）。不做通用协同 OT。
- **成本**：0.5–1 天。**落点**：`BitableEditor.tsx` 的写入口收敛 + 一个新的 `useBitableHistory` hook。
- **风险**：与自动保存的交互（撤销后仍会保存，符合预期）；与 `flushNow` 的时序。

#### 3.2 键盘导航 + 跨格块粘贴
- **主流**：Tab/Enter/方向键在单元格间移动、Enter 进编辑、Esc 退出；从 Excel/表格粘贴 TSV 直接铺开。
- **我们现状**：`[实测]` 只有选区 `⌘C/⌘V`（单值文本），无 Tab/Enter 导航、无多行多列粘贴。
- **为什么真**：多维表的第一使用场景就是**批量录入**，纯鼠标逐格点效率极低。
- **建议**：方向键/Tab/Enter 移动选区 + 进入编辑；粘贴时按 `\t`/换行 解析成矩阵填入。
- **成本**：0.5–1 天。**落点**：`BitableEditor.tsx` 网格 keydown + `pasteSelection`。

### P1

#### 3.3 分组（多级 + 折叠）
- **主流**：全部具备；是**看板视图的前置**。
- **我们现状**：`[实测]` 无；`BITABLE-PRODUCT-SPEC` 已记「v1.5」。
- **建议**：做。按某字段分组渲染组头（字段名+组值+折叠箭头+组计数），多级可选；持久化在视图配置（`BitableView.groups`）。
- **成本**：1–1.5 天（含数据模型升版与同步兼容）。**落点**：`bitableDoc.ts` 视图结构 + `BitableEditor` 渲染。

#### 3.4 冻结列 / 行
- **主流**：宽表必备。
- **我们现状**：表头 `th` 已 `position:sticky`，**列未冻结**。
- **建议**：做（低成本）。首列（主字段）或用户指定列冻结。
- **成本**：0.3 天。**落点**：`bitableEditor.css` + 视图配置。

#### 3.5 大表虚拟化
- **主流**：千行级网格滚动流畅。
- **我们现状**：`[实测]` `shownRecords.map` 全量 DOM；开发库记录数未知，量级未实测。
- **建议**：**先造 2k/5k 行合成数据实测耗时再定**（对齐 `HANDOFF §3.0(d)` 目录树的做法）。量到卡再做窗口化；不卡就不做（红线 #17）。
- **成本**：先测 0.2 天；真做 1–2 天。

#### 3.6 CSV / Excel 导入导出
- **主流**：全部支持，是数据进出的基本盘。
- **我们现状**：`[实测]` 无（用户 260919「本期不做」）。
- **建议**：**建议复议**。理由：① 本地优先应用对「数据可带走」有更强诉求；② 导入 Excel/CSV 是从电子表格迁移进来的唯一低摩擦入口；③ 导出是防止数据被锁死的保险。可只做 **CSV 导出 + CSV/TSV 粘贴导入**（不引 xlsx 依赖），成本低。
- **成本**：CSV 导出 0.5 天；粘贴导入随 3.2 一起。**落点**：`electron/noteExport.ts` 已有非 doc 守卫，可扩展；目录树右键菜单。

### P2

#### 3.7 视图类型扩展：看板 / 画册 / 日历
- **主流**：核心三件（看板按分组、画册按图片、日历按日期）。
- **我们现状**：`views[]` 已保留结构位（`BitableViewType` 现为 `grid|form`）。
- **判断**：**看板**价值最高（任务流转，依赖 3.3 分组）；画册/日历其次。建议**先看板**，其余按真实需求再开（不做齐）。
- **成本**：看板 1–2 天。

#### 3.8 筛选条件组（AND/OR 嵌套）+ 条件着色
- **主流**：`添加条件 / 添加条件组`；按条件给行/单元格着色。
- **我们现状**：`[实测]` 仅扁平 AND；无着色。
- **判断**：OR 组中等价值；条件着色是「一眼看出状态」的高性价比增强。建议**先做条件着色**（低风险），OR 组后置。
- **成本**：着色 0.3–0.5 天；OR 组 0.5 天。

#### 3.9 字段类型与格式扩展
- **主流**：货币/百分比/时长、勾选框、评分、进度、链接/邮箱/电话、自动时间。
- **我们现状**：用户 260919 已否掉「文本扩展类」。
- **判断**：尊重既有决策，**不铺开**。只有两项值得单独评估：
  - **数字格式（精度 / 千分位 / 百分比）** —— 是「数字」字段的属性，不是新类型，成本低、收益明确；
  - **创建时间 / 修改时间（只读自动字段）** —— 单用户也能用（排序/筛选「最近改动」），但注意无协作语义下「修改人」不做。
- **成本**：各 0.3 天。

#### 3.10 计算类字段（公式 / 关联联动 / 查找引用 / 汇总）—— 最大的结构性缺口
- **主流**：Airtable/Notion 的 formula + lookup/rollup + linked records 是「数据库」区别于「表格」的核心；飞书/SeaTable/Teable 同样齐备（`[调研]`）。
- **我们现状**：`[实测]` 无公式；关联只占位不联动；无 lookup/rollup。
- **用户口径**：`BITABLE-PRODUCT-SPEC §3.1`「大部分需求是结构化存储 + **简单公式**」，但 §3.3 把公式/查找引用/汇总列为**不做**（等「多数据表关联」时再议）。
- **判断**：这是**唯一一个会改变产品定位**的缺口——不做，多维表永远只是「带类型的清单」；做了，才接近「本地数据库」。但成本高、易过度设计。建议**单独立项、先定边界**：
  1. 先做**关联联动**（单向 link 能选本doc其它表的记录）——复用已有 `relation.tableId` 占位；
  2. 再做**简单公式**：只支持字段引用 + 四则/连接/条件（`IF`）等**无副作用子集**，不引入完整表达式引擎/脚本；
  3. lookup/rollup 依赖关联，最后做。
- **成本**：关联联动 1–2 天；简单公式 2–4 天（含依赖重算与脏值策略）。**这是建议单独立项、不要顺手做的一项。**

### 不做（附理由）

| 项 | 理由 |
|---|---|
| 协作 / 权限 / 分享收集 / 评论 | 本地优先、单用户，做了是假模型（产品红线） |
| 自动化 / Webhook / API / 插件 | 无服务端；与「本地优先」定位冲突 |
| AI 字段 / AI 筛选 / AI 填色 | 无后端与密钥方案，且 `AGENTS #17` 反对为概念堆功能 |
| 仪表盘 / 图表视图 | 价值成立但成本高、与我们「笔记应用」主定位偏离；等真有分析需求再说 |
| 记录正文（每条一篇 Lake 富文本） | 用户 260919 明确否决（「一条一个 Lake 太奢侈」）；且每条挂内核实例成本高 |
| 逐列统计 / 汇总栏 | 用户 260919 明确「不做」；若复议，仅建议做**单选/数字列的轻量计数/求和**（成本低） |
| 人员 / 部门 / 创建人 / 修改人 | 无协作模型，做出来是假字段 |
| 地图 / 甘特 / 透视表 / 查询页面 / 排版打印 | 长尾视图，未证需求 |
| 移动端可编辑多维表 | 当前移动端多维表为只读占位；是否升级取决于移动端是否要承接结构化录入（单独决策） |

## 4. 建议的下一批（Top 5，按顺序）

> 全部避开「已定不做」，且每条都能独立验收。

1. **撤销/重做**（P0，0.5–1 天）——防数据损失，最高性价比。
2. **键盘导航 + TSV 块粘贴**（P0/P1，0.5–1 天）——录入效率，与 1 同一批做。
3. **冻结列 + 大表性能实测（先测后定虚拟化）**（P1，0.5–1 天）——宽表/大表可用性。
4. **分组（多级 + 折叠）**（P1，1–1.5 天）——视图能力，且是看板前置。
5. **CSV 导出 + 粘贴导入**（P1，0.5 天）——数据可带走，本地优先最该有。

**单独立项（不并入上述批次）**：**关联联动 + 简单公式**（§3.10）——先出边界文档再动手。

**建议先测量再决定**：大表虚拟化、移动端可编辑多维表——都需要先有量级/使用证据（`AGENTS #17`）。
