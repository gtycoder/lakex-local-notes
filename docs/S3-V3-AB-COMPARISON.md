# master 旧同步 vs v3 真实 S3 A/B（261025）

> **261026 状态：历史报告**。旧引擎（`src/core/syncEngine.ts`）与对照测试 `electron/s3v3/ab.integration.test.ts` 已删除，本文件只保留当时数据。
> 目的：同一批真实桌面 Store 数据、同一真实七牛桶，分别跑 master 旧引擎（manifest 链）与 v3（不可变索引/pointer），对比耗时、对象数、字节数。
> 测试：electron/s3v3/ab.integration.test.ts（S3V3_AB=1）。每档都新建两份独立 Store（文档正文约 900B，无附件），两个独立 S3 前缀，结束后 deleteByPrefix 清空。

## 结论（优缺点）

### v3 优点
1. **零变更同步快 12~53 倍**：v3 读 pointer + 比对索引即可判定无变化（100 文档 71ms / 500 文档 156ms）；旧引擎每次都要拉/校验 manifest 链并重新对账（1.7~8.3s），随文档数线性增长。
2. **初始上传快 1.3~1.8 倍**：v3 全局上传队列（≤8）+ 单索引；旧引擎 manifest 组装/流式上传/链式收尾额外开销。
3. **无附件时字节更少约 4.7%**：v3 索引 96,918B vs 旧 101,753B（100 文档）；500 文档 480,782B vs 504,629B。
   **有附件时字节多约 3.6%**（615,215B → 637,491B），多出的主要是每个有附件笔记一份不可变资产声明（声明让「零痕迹/附件版本门禁」可判定，是 v3 的必要成本）。
4. **对象数**：无附件时相当（+1：quick-notes 空索引/pointer）；有附件时多 101 个（100 篇各一份资产声明），属声明式设计的固定开销。

### v3 缺点 / 待优化
1. **增量同步慢约 1.5~2.2 倍**（改 5 篇：旧 0.32/0.45s，v3 0.69/0.99s）：v3 每次发布都重写整份不可变索引（500 文档约 60KB）+ 发布读回 + pointer 锁流程；旧 manifest 也是整份写，但省掉读回/锁与适配器全量映射。
2. **索引随文档数线性增长**：2 万文档索引约 5.4MB（合成测试），发布一次即整份 PUT；旧 manifest 同量级但回收链更复杂。目标 10 万文档前需要 per-notebook/分片索引（v3.1 已预留），否则单对象 PUT/GET 会成瓶颈。
3. **适配器全量映射开销**：每次同步扫描 Store 全部笔记元数据；500 文档零变更仍 156ms（可接受），2 万文档需实测。

### 共同点 / 正确性
- 两端上传条数一致（101/501），说明没有漏传/重传。
- 旧引擎遗留 manifest 链（保留 N 份）；v3 不可变索引 + pointer，旧索引靠深度清理回收。
- 本 A/B 只覆盖「单设备初始/空跑/增量」，未覆盖冲突、删除零痕迹、多端；这些在双端假 S3 / 真实 S3 集成测试中单独验证。
