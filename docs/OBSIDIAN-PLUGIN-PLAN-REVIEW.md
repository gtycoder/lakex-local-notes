## 0. 总判定

**方案可以落地，方向论证成立。** MD 生态 vs 专有引擎的三条论证主线经核对全部成立（但其中一条的论据需修正，见 §1）。§19 的重标注整体准确，我核出 **4 处标注偏差**（Obsidian 原生能力被低估：File Recovery / 导出 PDF / 草稿覆盖）和 **3 处方案需补强点**（画板构造选择、同步数据可逆性缓解、粘贴拦截占坑）。

## 2. 逐答 §16 的 7 个问题

### Q1. CM6 悬浮块工具栏可行性与坑 —— ✅ 可行，是工程量问题不是可行性问题

- 先例：Notion Block 插件用 CM6 decorations 在 Live Preview 上做块把手/拖拽/转换菜单，证明"块级浮动 UI"这条路走得通；社区另有多个 editor-toolbar 类插件。
- 已知坑（均可解，spike 确认即可）：
  1. **焦点保持**：工具栏按钮 mousedown 必须 preventDefault，否则丢选区——本项目移动端 EditorDock 已有完全相同的教训和现成解法（`onMouseDown preventDefault`）。
  2. **IME 组合期**：composition 期间不能打断 DOM/装饰更新，工具栏显隐逻辑要避开 composition 事件窗口。
  3. **Live Preview vs Source 双模式**：decoration 在两模式行为不同（Source 模式无渲染层），工具栏要么双模式适配要么只在 LP 提供。
  4. **与 Obsidian 全局快捷键/其他插件的冲突面**：keymap 要走 `Mod-` 前缀约定，冲突面可控。
- 结论：照做即可，无需 spike 出生死，spike 只需确认观感。

### Q2. 卡片 = Obsidian 构造 + CSS 皮肤，够不够像 Lake？—— 按"无损/近似/天花板"三级诚实分账

**✅ 无损或接近无损**（映射表 §6 对应项成立）：
段落/标题、加粗/斜体/删除线、`==高亮==`、链接、无序/有序/任务列表、引用、代码块、分隔线、折叠块(callout)、高亮块(callout)、图片 embed、音频/视频 embed 原生内嵌播放、附件 embed。

**⚠️ 近似但体验打折**：
- **表格**：MD 表格无合并单元格、无列宽拖拽；Obsidian 内置表格编辑器够用但不是 Lake 表格卡体验。复杂表格（合并/嵌套）是映射表里隐藏的最大降级点，§6 未点出。
- **自定义字体颜色**：`<span style="color:...">` 在 Live Preview/阅读模式可渲染，但选色交互、编辑态该行源码可见性要接受；方案已标 ⚠️，判断正确。
- **思维导图**：mermaid mindmap / markmap 都是"改文本→重渲染"，**不是 Lake 导图的节点直接拖拽编辑**。功能在、交互模式变了。
- **画板**：§6 选 Obsidian Canvas——**这条建议改**。Canvas 是"节点-连线"板（类白板笔记），不是 Drawnix 的自由图形画板；且 .canvas 嵌入 md 后编辑要跳出当前文档。**更贴的构造是 Excalidraw 插件**：`.excalidraw.md` 本身是 md 文件（可搜索可嵌入可双击编辑），自由绘图体验接近 Drawnix，社区最成熟（数千 star）。代价是引入强第三方依赖。建议 §6 把画板行改为"Excalidraw（首选）/ .canvas（备选）"，Phase 0 两个都试。
- **表情/日期**：✅ 无问题。

**❌ 天花板（承认做不到，无需再试）**：
- Lake 的真 WYSIWYG（块内即时所见、无源码态）——CM6 叠加层永远做不到，这是 MD 方案的固有边界，§8.4 已声明，接受即可。
- 画板/导图的原引擎编辑体验（同上，构造已换）。
- 加密卡片（方案已暂缓，无异议）。

**给用户的直白话**：工具栏观感能做到 ~95% 像；"结果与 Lake 一致"在文本类卡片 ~95%，在 **表格/导图/画板** 三类构造上大约 60-70%（能用，交互逻辑不同）。这正是"要不要接受"的关键判断点——**必须亲手摸过再拍板**。

### Q3. 附件模块 —— ✅ 路径合理，代码复用主张已核实为真，补 4 个坑

**代码核实**（我逐一查了源码，方案没有幻觉引用）：
- `src/core/assetNaming.ts`：`ASSET_NAME_RE = /\d{13}_[0-9a-f]{8}\.[a-z0-9]{1,10}/g`、`isImageExtension`、`isAssetExtension` ✅ 存在，直接复用。
- `src/features/editor/imageFormat.ts`：`sniffImageFormat`（魔数）✅ 存在。
- `src/features/editor/resourceUpload.ts`：`createConcurrencyQueue`/`withRetry` ✅ 存在（并发 6+重试 2 次指数退避）。
- `docs/MARKDOWN-EXPORT-REVIEW.md`：lake→md 全文转换实测"完美"（`editor.getDocument("text/markdown")`，registerReader/Writer 源码确认）✅——**§15 迁移路径有实证支撑，这是方案最扎实的部分之一**。

**方案没写到、需要补的坑**：
1. **粘贴拦截要占在 Obsidian 默认处理之前**：Obsidian 原生"粘贴图片"有自己的附件目录逻辑，会先落盘。插件必须用 CM6 `EditorView.domEventHandlers({paste, drop})` 捕获并处理，否则分类/命名/限长被绕过。可实现，但要写进 §7.1 第 1 步。
2. **`vault.createBinary` 同名冲突**：内容寻址下重名=同内容（可复用），但 `createBinary` 对已存在文件的行为需处理（先 `getAbstractFileByPath` 判存在，存在即复用引用不重写）。
3. **webp→png 统一用 Canvas，建议彻底放弃 sharp**：Chromium decode webp/avif → canvas → `toBlob('image/png')`，png 是无损重编码（损失只在源图已有），质量无虞且桌面/移动一个代码路径。sharp 在桌面插件可用但要按 Obsidian 的 Electron ABI 预编译+追随升级，**收益不抵维护成本**。§7.2 应把 Canvas 定为主案、sharp 删除或降为"明确不做"。
4. **移动端粘贴遗留问题重新验**：现安卓端"剪贴板粘贴不解析为空"的遗留 bug 在 Obsidian mobile 的 paste 路径下要重新验证（机制不同），列入 Phase 3。
- 复制到微信（桌面 `clipboard.writeImage`）：可行（桌面插件可 `window.require('electron')`）；移动端弱/降级——方案判断正确，接受。

### Q4. 小记建模 —— ✅ 方案可用，补 3 个细节

- **建议独立目录 `QuickNotes/` + 插件面板，不用 daily notes**：daily notes 是"每天一篇"，小记是"每条一卡"时间线，模型不同；§9 的行为对齐（手动记下/5 秒撤销/转正式）在插件面板 + md 落盘下可完整复刻。删除语义走 Obsidian `.trash` 反而比"5 秒后 tombstone"更安全。
- **"转为正式笔记 = 插到笔记本最顶部"的语义要重新定义**：md 没有 sort_order，Obsidian 文件树默认按名称排序。解法：文件名加序号前缀（`NNN_`）或 frontmatter `created` + 自定义排序。§9 需补这一句，否则"插顶"落不了地。
- **小记图片目录**：§5.2 未列小记图片的落点，补 `quick-assets/{quickNoteId}/`（或并入 lake-assets，但要与小记"独立空间"语义一致）。
- 转换 journal/冲突副本归档等重机制：MD+简化同步下【简化】判断正确，无需保留 journal 级一致性（转正式本质是"复制内容→新建 md→删源文件"，文件系统天然可恢复）。

### Q5. 同步 —— ✅ Remotely Save 大概率可连七牛；**真正的决策点不是连通性，是"误删/覆盖后数据还能不能找回"**

- **连通性**：S3-compatible 通用通道 + `requestUrl` 绕 CORS 后，剩余风险只有 endpoint/path-style 兼容，实测半天内可出结论，风险小（研究纪要标【需谨慎】合理）。
- **语义降级的真实敞口**（§12 已列，我把"哪些会真的咬人"排个序）：
  1. **最痛：冲突处理 keep newer/larger = 直接丢掉输掉的一边**。现方案"冲突生成 (冲突副本 日期) 笔记+被覆盖自动留档"是数据不丢语义；Remotely Save free 版没有 keep both。**双端同时改同一篇 = 必有一边的数据没了**。
  2. **次痛：删除传播无墓碑**——删除会同步（Remotely Save 处理删除），但"恢复标记 local-wins"没了；好在删除的文件进 Obsidian `.trash`/系统废纸篓，本端可救。
  3. **GC 语义消失**：未引用资产永久累积（现方案有 7 天保留窗口 GC + 历史引用保护）。可忍受或用"未引用清理"类插件补。
- **强烈建议把缓解措施写进 §12（方案目前没写）**：**标配 Obsidian Git 插件**（本地 vault 定时 commit + push 到私有仓库）。这是社区与 Remotely Save 的常见组合，成本近零，一次性补掉"keep newer 丢数据"和"误删已同步"两个最大恐惧——**有了 git 兜底，A/B 方案的语义损失就从"数据风险"降级为"体验损失"**，这是本复核最重要的单条建议。
- 决策树：单用户 + 一主一备使用习惯（手机看/桌面写）→ A/B 可直接用；双端高频交替写同一文档 → 上来就做 §12 C（自研引擎移植，syncEngine 端口化可搬，但 vault adapter + fetch 版 S3 sigv4 是方案里最大单体工程，别低估）。

### Q6. 有无遗漏？—— §19 整体准确，核出 4 处标注偏差（均为 Obsidian 原生能力被低估）

| §19 条目 | 原标注 | 应改为 | 依据 |
|---|---|---|---|
| §19.2 历史快照（15min 自动/恢复/预览） | 【插件/简化】"Obsidian 无文档级历史" | **【原生(大部分)】** | Obsidian **核心插件 File Recovery** 默认按间隔对全 vault 快照、可浏览/恢复任意文件任意历史版本，覆盖"自动快照+恢复+预览"的主场景。只有"手动快照/冲突自动留档/保留策略"需要插件 |
| §19.7 Word/PDF 导出 | 【插件/可选·未实现】 | **【原生/插件】** | Obsidian 原生就有 **Export to PDF**；Word 走 pandoc 社区插件。现 app 反而是"注册了没实现" |
| §19.2 草稿恢复 draft-journal | 【插件/简化】 | **【基本不需要】** | Obsidian 编辑防抖即写盘 + File Recovery 快照，"崩溃丢字"原始诉求基本被覆盖 |
| §19.5 MIME/Range/缓存 | 【插件·复用现有】 | **【无】** | 这些是自建 HTTP 资产服务的服务端机制，改 `app://`/vault 文件后由 Obsidian 资源协议承担，无需复用 |

另外补两条 §19 没有的白拿项：专注模式（社区插件/工作区布局）、模板（core Templates）、字数统计（原生状态栏）。

还有一条**语义变化要写明（非遗漏，是差异）**：笔记本树三级（笔记本/分组/文档）迁为纯目录后，**文件名即标题**——重命名文件=改标题，原"标题独立于文件名"语义消失；sort_order 消失。可接受，但要进迁移说明。

### Q7. 反方致命伤排查 —— 没有致命伤，但有一句必须摆在台面的话

1. **本质让步**：本方案买"搜索/生态/开放格式/可上架/数据主权"，付的是"放弃 Lake 真 WYSIWYG 与三类卡片（表格/导图/画板）的原生编辑交互"。这笔交易在 §1.2 已由用户拍板，复核确认**没有隐藏的更差后果**——最差的就是已经明说的这些。
2. **数据主权反而是升级**：纯 md + 纯文件，任何工具可读可逆，"跑偏了随时下车"的能力比 .lake 方案更强。对用户的原始焦虑（跑偏）这是最好的解药。
3. **API 漂移**：`registerEditorExtension`/decorations/`domEventHandlers` 是 Obsidian 生态最核心、依赖面最大的 API 群（上千插件押注），漂移风险实际低于小众 API。pin 版本+核心逻辑与 API 层隔离即可。
4. **迁移有损**：文本类无损（已实证），画板/导图/加密卡降级或丢失，历史快照/回收站状态/同步状态**不迁**（全新开始）。导出脚本要按卡片类型逐类处理+全量人工抽查。这个损失是**一次性的、可预览的**（迁之前可先跑导出脚本看结果再决定），不是盲赌。
5. 唯一让我犹豫过的反方论点："用户最看重工具栏，而工具栏在 CM6 上的手感与 Lake 原生有差"——但工具栏手感恰恰是 spike 能低成本验证的，构不成"方向性致命伤"，只构成"先摸再拍板"的理由。

## 3. 复核结论汇总：对方案的修订清单

**A. 论据修正（不改变结论）**
1. §1.3 第 3 条：删"走阿里 CDN"作为技术障碍的暗示，改为"已全量本地镜像可离线；弃用的真实理由=搜索/生态丢失+许可+闭源 vendor 脆弱性"。

**B. 方案内容修订（建议采纳）**
2. §6 画板行：改为 **Excalidraw 插件（.excalidraw.md）首选 / .canvas 备选**，Phase 0 双测。
3. §6 表格行：加注"MD 表格无合并单元格/列宽，复杂表格降级"——这是映射表里最大的隐藏降级点。
4. §7.1：粘贴拦截改为 CM6 `domEventHandlers` 捕获并 `preventDefault`（占坑在 Obsidian 默认粘贴之前）；补 `createBinary` 重名复用处理。
5. §7.2：转码主案定为 **Canvas/OffscreenCanvas（双端统一）**，sharp 移除（省 ABI 追随）。
6. §9：补"插顶"语义落地（文件名序号前缀或 frontmatter 排序）+ 小记图片目录 `quick-assets/`。
7. §12：**加一条标配缓解——Obsidian Git 插件做本地版本兜底**，并写明决策树（单主一备→A/B 可用；双端高频互写→直接 C）。
8. §15 迁移：写明"文件名=标题、无 sort_order、历史/回收站/同步状态不迁"三项语义变化。

**C. §19 标注修正**
9. 历史快照→【原生(大部分)】；Word/PDF 导出→【原生/插件】；草稿恢复→【基本不需要】；MIME/Range/缓存→【无】。

**D. Phase 0 spike 清单重排（按"信息量/成本"排序，优先摸体验天花板）**
1. 表格编辑（Obsidian 原生表格编辑器实感 vs Lake 表格卡）
2. 导图（mermaid vs markmap vs Lake 导图）
3. 画板（Excalidraw vs .canvas vs Drawnix）
4. 自定义颜色 span 的编辑态/选色交互
5. CM6 块工具栏+焦点保持+IME（观感验证）
6. 粘贴拦截占坑全链路（分类/命名/限长/重名复用）
7. Canvas webp→png 转码对比
8. 大文档性能（数 MB md + 多 embed/callout）

> 前 3 项是"用户拍板项"（体验天花板），后 5 项是"工程确认项"（大概率过）。建议 spike 产出可交互的 demo 让用户亲手用 10 分钟再定方向。

## 4. 最终意见

**方向成立，可进入 Phase 0。** 本复核未发现致命伤；发现的问题集中在：画板构造选型（建议 Excalidraw）、同步数据可逆性缓解（建议 Obsidian Git 标配）、4 处 Obsidian 原生能力被低估（§19 修正）、以及 1 处论据修正（CDN）。全部有解，且都有低成本验证路径。

**给用户的一句话**：这份方案换来的（搜索/生态/开放格式/移动端壳/上架可能/数据主权）比付出的（三类卡片交互降级 + 同步语义简化）值，前提是你**亲手摸过 spike demo 里表格/导图/画板三样之后仍然愿意接受**。
