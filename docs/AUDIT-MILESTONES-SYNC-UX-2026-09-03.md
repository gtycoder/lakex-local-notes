## 0. 既定产品契约（本次复核的判定基准，视为已接受、不可再争论）

| # | 契约 | 对审计的影响 |
|---|---|---|
| C1 | 本地优先、S3 只做镜像/备份 | 云端不可静默覆盖本地；但**用户显式恢复**是唯一允许的反向例外 |
| C2 | 个人笔记 | 无多人协作 / 无权限模型 / 无远端团队语义 |
| C3 | 多端、无并发 | 同一文档不并发编辑；"同时提交"是低频边界 |
| C4 | 先提交者为真（先同步者胜） | 晚提交的一方接受远端，其本地成果被判定为"被覆盖" |

> 结论：**C4+C5 使"冲突收口"不再是语义问题，而是"归档 + 提醒"体验；C6 使"回收站"的自动过期/倒计时/purge 文案与真实实现必须对齐。**

## 2. 不成立（在既定契约下被推翻 / 过时）

### 2.1 A2 = "违反红线①/②（云端反噬本地）" —— 不成立
- **契约支持**：C1（本地优先）+ C2（个人）+ C3（无并发）。云端仅在用户**显式发起**的"换机/坏库恢复"时作为数据源，属**唯一的反向例外**，与"恢复是唯一显式例外"（AGENTS §3.4 / TRASH-NOTEBOOK-DESIGN）同构。
- **为何不成立**：它不是后台/自动行为，不会在正常同步中发生，因此不构成"云端反噬本地"的红线违例。
- **但仍须守住（归 §4）**：恢复必须是**隔离备份 + 全新空库 + 只拉不打 + 显式确认**，且**禁止对现有库"重置同步态"**——否则会把本地存量误判为"并发新变更"，导致本地上传覆盖云端或反向覆盖。

### 2.2 B2 = "同步前确认门会改变'先提交者为真'语义" —— 不成立
- **契约支持**：C4（先提交者为真）+ C5（冲突自动留档）。
- **为何不成立**：用户**取消**预检只是选择"本轮不同步"（保持本地滞后），并不会改变云端已胜出的事实，也不会阻止后续留档/收敛；因此不构成对语义的破坏。
- **但仍须守住（归 §4）**：若保留 B2，预检判定必须与 `reconcileLakeNote` 同源（见 §4.2）。

### 2.3 "`trashAutoPurgeDays` 仅提醒、绝不自动执行" —— 不成立（过时）
- **契约支持**：C6（回收站=有笔记本行为的容器，自动过期是其生命周期）。
- **证据**：
  - `S3-GC-DESIGN.md` §7（line 213）/ §13.3（line 341）："默认 0=关闭；仅提醒、绝不自动执行"。
  - `TRASH-NOTEBOOK-DESIGN.md` D3（line 23）/ §4.7（line 83）："默认 60；真正自动过期；main.ts 定时 purge"。
  - 代码 `electron/store.ts:1772`（默认 60）、`electron/main.ts:508-517`（启动+每日真实 `autoPurgeExpiredTrash`）。
- **为何不成立**：代码与 TRASH 设计均已实现**真实自动过期**；S3-GC-DESIGN 的"绝不自动执行"是**未随 v4.1/TRASH 更新的过时表述**。
- **动作**：方案设计者应**以 TRASH-NOTEBOOK-DESIGN D3 / §4.7 为准**，并**修订 S3-GC-DESIGN §7/§13.3**（属文档纠偏，可直接提交）。

### 2.4 "purge 云端按 GC 窗口清除" —— 不成立
- **契约支持**：C6（purge=永久删除+立即镜像清理）+ 既有 purge 语义。
- **证据**：`electron/syncEngineController.ts:87-94`（`deletePrefix(objects/{id}-)`、`deletePrefix(assets/{id}/)`）、`electron/sync.ts:283-289`；设计 `S3-GC-DESIGN.md` D2（"先写 manifest(deleted:true) → 再按前缀立即删，不进窗口"）、`TRASH-NOTEBOOK-DESIGN.md §4.3`。
- **为何不成立**：purge 是**立即删除云端正文/资源**，**不进 GC 保留窗口**。M2-C2 文案"云端按 GC 窗口清除"**低估了云端数据不可恢复性**。应将文案改为"**本机立即移除 + 云端正文/资源立即删除且不可恢复 + 他端保留可恢复副本**"。

## 3. 没有必要修改（在既定契约下可简化 / 取消）

### 3.1 B2 的"同步前阻断确认"（"确认才继续"）—— 没必要
- **契约支持**：C5。被覆盖的本地成果**已自动留档**（superseded → `createHistorySnapshot`，`syncEngine.ts:541/593/703`），不会真的丢。
- **为何没必要**：既然冲突编辑不丢，冗长的"同步前清单确认"收益很低；B1（同步后 toast "N 份被覆盖已存档"）已能告知。
- **建议**：把 B2 **降级为非阻断提示**（不要求确认即可继续），或**并入 B1**；若坚持保留，只做信息展示，不做"取消则中止同步"的门。

### 3.2 A1 的"导出 + 恢复导入"选项 —— 没必要
- **契约支持**：C1 + 已有 A2（云端恢复）。
- **为何没必要**：A2 本身就是"恢复"路径；A1 再做"导出+恢复导入"会与 A2 重复（且 A2 覆盖云端方向）。A1 **只做导出**即可，既满足"数据不丢可由本地保证"，又缩小风险面。

### 3.3 B3 的"移动端同步 protected_until 保护语义" —— 没必要
- **契约支持**：C3 + C5（归档是本地行为）。
- **为何没必要**：移动端 `note_history` 是简化 schema（`src/mobile/bridge.ts:204` 无 `protected_until/file_path/refs_json/ref_count/size`），且**无 `cleanupHistory`**，不存在"自动清理误删受保护快照"的问题。
- **动作**：只需保证共享 `SyncDbPort.createHistorySnapshot` 扩签名时给移动端**默认 `protected=null`**，**不要**强求把保护语义同步到移动端。

### 3.4 B4 块级 Diff —— 没必要（建议取消 / 降为可选 backlog）
- **契约支持**：C2（个人）+ C3（无并发）+ C5（冲突不解决、自动留档、用快照预览即可）。
- **证据**：`S3-GC-DESIGN.md §14` 已明确："不建议为同步引入 block/行级对比…… 单用户场景下冲突极少且永不丢数据…… 真要看差异，用现有'历史快照预览'即可"。
- **为何没必要**：B4 的"块级 Diff 可视化"与既有"历史快照预览"（`HistoryPanel` 已实现）功能重叠；且 C5 下冲突本就是归档而非合并，块级对比对"同步/GC/安全"无增益。
- **建议**：**取消 B4**，或用现有快照预览承载；若坚持保留，仅作为独立分支 + 可选，须显式声明 `diff` 依赖（当前为传递依赖 `node_modules/diff@^5`，`package.json` 未声明）、加"只读"断言、性能基准可复现，且**不得占用主线优先级**。

## 4. 需要继续修改（硬约束，不改会出问题）

### 4.1 B3：`note_history` 加列 + `cleanupHistory` 跳过 + 到期解除
- **必须**：明确"受保护快照"的写入路径（superseded 时 `createHistorySnapshot` 需知道"这是冲突归档"），扩 `SyncDbPort.createHistorySnapshot` 签名（`src/core/syncEngine.ts:248` / `electron/syncAdapters.ts:145` / `src/mobile/bridge.ts:487`）。
- **必须**：`cleanupHistory`（`electron/store.ts:979-1010`）跳过 `protected_until > now` 的快照，并**在扫描内幂等**把已过期快照的 `protected_until` 清掉（否则永远逃逸保留策略）。
- **必须**：**手动删除任何时候允许**（不受保护限制）；保留 `cleanupUnreferencedAssetsForNote`（`store.ts:999`）引用的历史资源保护（GC keep-set `sync.ts:329-343` 已含 `getProtectedRefs`，**不受影响**，可放心）。
- **契约**：C5 下这是"冲突归档"的落地机制，方向正确；但保留期（30 天）是否够，建议与方案设计者确认（因归档是冲突的**唯一**记录，可考虑更长或"冲突归档不自动回收"）。

### 4.2 B2（若保留）：预检判定 must match reconcile + 只挂桌面手动
- **必须**：预检用 `reconcileLakeNote` 全量输入（`lakeReconcile.ts:15-21/58-85`，含 `lastSyncedMetaAt`、`remoteUpdatedAt`、`localInTrash`），不只 `baseHash/lastUploadedHash`，并**先算覆盖集再应用**。
- **必须**：只在桌面 `sync_now` controller 层触发（`registerSync.ts:147-154`）；**绝不进入共享 `runSyncEngine`**，否则 interval/onOpenClose/重开同步也会触发（违反"自动同步绝不弹"）。
- **契约**：C4+C5 下，冲突收口是"提醒"，无需在预检里做语义判断，只需保证提示与实际覆盖一致。

### 4.3 C1：倒计时数据源 + 0=关闭边界
- **必须**：用 `list_trash`（每项 `TrashItem.deletedAt`=`trashed_at`，`src/core/trashRepository.ts:66-68`）+ `get_s3_gc_settings`（`trashAutoPurgeDays`）**派生**"剩余 N 天"，**不要**用 `get_trash_reminder`（其 `listReminder` 只返回**已过期**项：`trashRepository.ts:82-95` `deletedAt < cutoff`）。
- **必须**：处理 `0=关闭`（`listReminder` 对 `days<=0` 返回 `[]`，`trashRepository.ts:81`）——此时**不显示倒计时/提示条**，并确保 auto-purge 不运行（`main.ts:513` `<=0 return`）。
- **必须**：把 `trashAutoPurgeDays` 语义与代码（默认 60、真实自动过期）及 `TRASH-NOTEBOOK-DESIGN` 对齐，修订 `S3-GC-DESIGN` §7/§13.3。
- **契约**：C6 下显示"N 天后自动清除"是合理的；但须与"真实自动过期"一致，且标黄（≤7 天）为纯展示，不改变自动过期行为。

### 4.4 C2：purge 文案
- **必须**：改为"本机立即移除 + 云端正文/资源立即删除且不可恢复 + 他端保留可恢复副本"，与 §2.4 一致。

### 4.5 A2：机械安全（在"不成立"之上仍须守住）
- **必须**：隔离备份 → **全新空库** → **只拉不打**（本次不上传任何本地变更）→ 显式确认 → 完成报告；**禁止对现有库"重置同步态"**；并保证恢复期间不反向覆盖本地/云端。

### 4.6 A3 / F1 / F3：IPC 三处 + 只读
- **必须**：新增 IPC（A3 `run_data_health_check`、F1 日志、F3 `get_last_history_cleanup`，后者 `store.ts:1863` 已实现但无 handle/无 preload/无 native 类型）补齐 **main handle + preload.cjs + native.ts**。
- **必须**：A3 为**只读**（不触发写/DOM/HTTP），并尽量放 `electron/` 而非 `src/core/`（守 `node:` 禁入）。

### 4.7 A1 / D1 / D2 实现
- A1 **只导出**（一致性快照 + 拷贝 .lake/assets/history/设置）。
- D1 顶栏浮层页脚（`SyncStatusPopover.tsx` footer 现仅有"同步设置"）"上次成功同步 · 未同步 N 项"。
- D2 渲染 `gcPendingRows`（`SettingsPanel.tsx:74,84,98` 已加载未渲染；需渲染 键+原因+到期）。
